# Codex 实战：如何安全地让 AI 编写和测试代码

## 30 秒快速回答

> 我使用 Codex 时，不会只说“帮我实现这个功能”，而是会明确目标、修改范围、不能破坏的约束、验收标准和验证命令。开始前让它阅读仓库结构、适用的 `AGENTS.md`、现有实现和测试；实现时要求最小改动，不擅自删除文件、升级依赖或操作生产环境；完成后按静态检查、单元测试、集成测试、E2E、构建和人工验收逐层验证，并检查最终 diff。测试通过也不等于一定正确，我还会核对业务边界、兼容性和未覆盖风险。对于 Codex 本身的效果，则使用“应触发样例、合法反例、无关样例”组成回归集，同时观察检出率、误报率和建议是否可执行。Codex 是开发和审查助手，不能替代 CI、分支保护和人工审批。

## 一、Codex 适合解决什么问题

Codex 更像一个能够读取仓库、调用工具、修改文件并运行验证的工程协作者，而不只是代码补全工具。它适合：

- 理解陌生代码和解释调用链；
- 修复能够复现的 bug；
- 在明确约束下实现小到中型功能；
- 补充测试、重构重复代码和迁移 API；
- 检查 diff 中的缺陷、兼容性风险和测试缺口；
- 执行 lint、测试、构建、基准测试并整理证据。

它不应该直接替代产品决策、架构责任、安全审计或上线审批。需求含糊、生产风险高、缺少业务知识时，应先缩小问题或由人补充决策。

## 二、一个高质量任务应该包含什么

“把这个页面优化一下”没有明确完成标准，Codex 很容易做出看似合理但不符合预期的修改。一个可执行任务至少包含以下信息：

| 信息 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 目标 | 最终什么行为必须成立？ | 未登录用户访问订单页时跳转登录页 |
| 范围 | 可以修改哪些模块？ | 仅修改路由守卫及相关测试 |
| 约束 | 什么不能改变？ | 不改变已有登录 API，不新增依赖 |
| 验收标准 | 如何判断功能正确？ | 登录态保留原行为，未登录态携带回跳地址 |
| 验证方式 | 用什么证据证明？ | 指定单测、E2E、类型检查和构建命令 |
| 停止条件 | 什么时候应停止并报告？ | 需要生产凭据、需求冲突或测试环境不可用 |

### 可直接复用的任务提示词

```text
请先阅读适用的 AGENTS.md、项目清单、相关实现和现有测试，再处理任务。

目标：未登录用户访问 /orders 时跳转到登录页，并保留原地址用于登录后返回。
范围：只修改路由守卫及相关测试。
约束：不改变登录 API，不新增依赖，不重构无关代码。
验收标准：
1. 未登录访问 /orders 会跳转到 /login，并携带安全的回跳地址；
2. 已登录用户行为不变；
3. 外部地址不能被用作回跳地址；
4. 相关测试和构建通过。

请先检查当前实现并说明最小修改方案，然后实现、运行由小到大的验证。
最终报告修改文件、实际执行的命令和结果、未执行的测试及剩余风险。
如果需要凭据、生产操作或扩大范围，请停止并说明原因，不要自行绕过。
```

## 三、推荐工作流程

### 1. 先建立上下文

让 Codex 先读取真实仓库，而不是根据常见项目结构猜测：

1. 阅读从仓库根目录到目标目录适用的 `AGENTS.md`；
2. 查看 `package.json`、构建配置、测试配置和 CI 文件；
3. 搜索相似功能、公共组件、类型和现有测试；
4. 确认当前工作区是否已有用户修改，避免覆盖无关 diff；
5. 找到项目真实使用的验证命令，不凭空编造命令。

`AGENTS.md` 适合保存长期、仓库特有的约束，例如编码规范、测试命令、兼容性要求、禁止访问的目录和审批边界。规则应简短、具体并限定作用范围；格式化等能够确定执行的检查应继续放在 lint 或 CI 中。

### 2. 先复现，再修改

修 bug 时应先得到失败证据，例如失败测试、错误日志或稳定复现步骤。这样可以区分“修复了根因”和“改到现象暂时消失”。

推荐采用 Red → Green → Refactor：

- **Red**：添加或找到能够暴露问题的最小失败测试；
- **Green**：做满足测试的最小实现；
- **Refactor**：只在行为保持不变且测试仍通过时整理代码；
- **Verify**：执行相关测试和更广的回归检查，核对最终 diff。

并非每个文档或样式改动都需要先写失败单测，但必须选择与风险匹配、真正能够证明结果的验证方式。

### 3. 小步修改，小步验证

不要一次同时做功能、重构、升级依赖和格式化全仓库。修改面越大，越难判断失败原因，也越容易把用户已有改动混入结果。

每一步都应回答：

- 改动是否直接服务于目标？
- 是否改变了公共 API、数据结构或持久化格式？
- 是否需要兼容旧调用方和旧数据？
- 是否增加了新的安全、性能或可观测性风险？
- 当前测试是否真的覆盖了这次行为变化？

### 4. 用证据结束任务

“代码看起来没问题”“理论上应该通过”不是验证结果。最终报告应该区分：

- 实际运行并通过的命令；
- 实际运行但失败的命令及失败原因；
- 因环境、凭据或时间限制没有运行的验证；
- 仍需人工检查的行为和剩余风险。

## 四、使用 Codex 的注意事项

### 1. 默认追求最小改动

优先沿用现有架构、类型、组件和工具。不要为了一个局部需求顺手替换框架、重写整个模块或修复无关问题。发现额外问题可以报告，但未经确认不要扩大范围。

### 2. 明确权限和副作用边界

以下操作可能难以恢复或影响外部系统，应要求显式确认：

- 删除或覆盖大量文件、重写 Git 历史；
- 推送代码、合并 PR、发布版本或部署；
- 执行数据库迁移、写入生产数据；
- 发送邮件、消息或创建外部工单；
- 安装来源不明的脚本，或执行需要高权限的命令。

读取文件、搜索代码、运行本地只读检查通常风险较低；一旦涉及外部写入、生产资源和不可逆操作，就应缩小权限并设置人工审批。

### 3. 不要泄露敏感信息

不要把 `.env`、API Key、Cookie、访问令牌、客户数据或生产日志原样放入提示词、测试夹具和提交记录。测试应使用脱敏数据和低权限、短生命周期凭据，输出日志时也要检查是否意外打印秘密。

### 4. 警惕“幻觉 API”

Codex 可能生成名称合理但项目中不存在的函数、配置项或包版本。处理陌生 API 时应：

- 搜索仓库当前依赖和锁文件；
- 查看安装版本对应的类型声明或官方文档；
- 编译并实际运行关键路径；
- 不因代码语法正确就假设 API 一定存在。

### 5. 编译通过不代表行为正确

类型检查只能证明一部分静态约束，不能证明权限、并发、缓存、数据兼容性和用户体验正确。单测通过也可能只是断言写错或 mock 掩盖了真实集成问题，因此需要按风险补充集成测试、E2E 和人工验收。

### 6. 保护兼容性

重命名字段、事件名、路由、环境变量和导出函数，即使项目能够编译，也可能破坏旧客户端或外部消费者。修改公共接口前要搜索所有调用方；必要时保留旧接口、增加兼容层，并添加覆盖旧行为的回归测试。

### 7. 审查最终 diff

交付前至少检查：

- 是否出现与需求无关的文件或大面积格式变化；
- 是否误删错误处理、埋点、兼容逻辑和注释中的业务约束；
- 是否把调试日志、临时开关、快照或敏感数据提交进去；
- 测试是否验证外部行为，而不是机械复述实现；
- 实际改动是否与最终总结一致。

## 五、如何测试 Codex 产生的代码改动

测试策略应由小到大：失败越早、定位成本越低。具体命令以仓库脚本和 CI 配置为准，下面的命令只表示常见类别。

| 层次 | 主要验证内容 | 常见方式 |
| --- | --- | --- |
| 静态检查 | 语法、类型、规范和明显错误 | TypeScript、ESLint、格式检查 |
| 单元测试 | 纯函数、组件状态、边界条件 | Vitest、Jest、React Testing Library |
| 集成测试 | 模块、数据库、缓存或 API 协作 | 测试数据库、Mock Server、接口测试 |
| E2E | 真实用户关键路径 | Playwright、Cypress |
| 构建验证 | 打包、SSR、路由和环境配置 | 项目 build 命令 |
| 人工验收 | 视觉、文案、可用性和真实业务语义 | 浏览器、真机、无障碍检查 |

### 1. 先跑最相关的测试

例如修改金额格式化函数，先运行该函数的单测；修改登录流程，先运行认证相关测试。不要一开始就运行耗时很长的全量 E2E，也不要只跑全量测试而忽略直接覆盖改动的用例。

```bash
# 以下是示意，实际项目应从 package.json 和 CI 中确认命令
npm test -- path/to/affected.test.ts
npm run typecheck
npm run lint
```

### 2. 测试正常、边界和失败路径

至少考虑：

- 正常输入和核心成功路径；
- 空值、极值、重复操作和非法输入；
- 网络失败、超时、取消和重试；
- 无权限、登录过期和越权访问；
- 旧数据、旧调用方和回滚后的兼容行为；
- 并发请求、重复提交和幂等性。

### 3. 再跑跨模块回归和构建

相关测试通过后，再执行项目约定的更广验证。例如前端页面改动通常还应检查：

- 生产构建是否成功；
- SSR 与客户端 hydration 是否一致；
- 路由直达和刷新是否正常；
- 桌面端、移动端和不同权限状态；
- Console、Network 和服务端日志是否出现新错误。

### 4. 不要用修改测试来掩盖失败

如果测试失败，先判断是产品行为改变、实现错误、测试环境问题，还是测试本身过时。不能仅为了“变绿”而删除断言、扩大 mock 或跳过测试。确实需要更新断言时，应解释旧预期为什么失效，并让新断言对应明确的需求变化。

### 5. 前端项目怎么测试

前端测试不能只验证函数返回值，还要验证用户在不同数据、网络、权限和设备状态下，能否正确看到页面并完成操作。可以按照下面的顺序执行：

1. **静态检查**：运行 TypeScript、ESLint 和格式检查，发现类型错误、未使用变量、错误的 Hooks 依赖等问题；
2. **组件测试**：使用 Vitest 或 Jest 配合 Testing Library，从用户视角验证输入、点击、提交、加载、空数据、成功和失败状态；
3. **集成测试**：验证组件、状态管理、路由和接口之间的协作，可使用 MSW 模拟成功、超时、错误码和异常响应；
4. **E2E 测试**：使用 Playwright 或 Cypress 覆盖登录、下单、支付、权限控制等关键用户路径；
5. **生产构建**：检查打包、SSR、客户端 hydration、动态导入、环境变量和生产路由；
6. **人工验收**：检查桌面端与移动端布局、键盘和焦点操作、慢网与断网状态、Console 报错以及 Network 请求。

组件测试应断言用户可以观察到的行为，不要过度依赖组件内部 state、私有方法或 DOM 结构。例如：

```tsx
render(<LoginForm />)

await user.type(screen.getByLabelText('邮箱'), 'user@example.com')
await user.type(screen.getByLabelText('密码'), 'password')
await user.click(screen.getByRole('button', { name: '登录' }))

expect(await screen.findByText('登录成功')).toBeVisible()
```

接口相关页面不能只测试 `200 OK`，还应覆盖：

- 首次加载、空数据和分页结束；
- 请求超时、断网、服务端错误和返回数据缺失；
- 重复点击、快速切换条件、请求乱序和取消；
- 登录过期、无权限和不同角色可见性；
- 表单边界值、错误提示、提交中禁用和重复提交。

E2E 应优先覆盖高价值业务链路，而不是把每一个组件细节都重复测试。一个典型用例如下：

```ts
test('用户可以完成登录', async ({ page }) => {
  await page.goto('/login')
  await page.getByLabel('邮箱').fill('user@example.com')
  await page.getByLabel('密码').fill('password')
  await page.getByRole('button', { name: '登录' }).click()

  await expect(page).toHaveURL('/dashboard')
})
```

最后要注意：构建通过只能证明应用能够被打包，不能证明交互、视觉和业务逻辑正确；自动化测试通过也不能代替真实浏览器中的人工验收。

### 可直接复用的验证提示词

```text
请验证当前改动，不要只阅读代码后推测结果。

1. 从 package.json、测试配置和 CI 中确认真实验证命令；
2. 先运行直接覆盖改动的最小测试，再运行类型检查、lint、相关集成测试和构建；
3. 为新增或改变的行为检查正常、边界、失败和兼容路径；
4. 如果失败，判断失败是否由本次改动引起；只修复范围内的问题，不要通过删除断言或跳过测试掩盖失败；
5. 检查最终 diff 是否包含无关改动、调试代码或敏感信息；
6. 最终逐项报告实际命令、退出结果、失败原因、未运行项和剩余风险。

未经实际执行，不要声称测试通过。
```

## 七、常见错误做法

| 错误做法 | 风险 | 改进方式 |
| --- | --- | --- |
| 只说“帮我优化” | 范围和完成标准不确定 | 明确目标、边界、验收标准和验证证据 |
| 不让 Codex 查看仓库 | 容易编造结构和 API | 先搜索现有实现、依赖、测试和约定 |
| 一次修改太多模块 | 难审查、难定位回归 | 小步修改，每步运行相关验证 |
| 只看最终回答 | 回答可能与真实 diff 不一致 | 检查 diff、命令输出和生成文件 |
| 把测试通过等同于零风险 | 测试可能缺少业务边界 | 补充兼容性、安全和人工验收 |
| 让 AI 自由处理生产系统 | 可能造成不可逆副作用 | 最小权限、沙箱环境、人工审批和回滚方案 |
| 只测试规则的正例 | 无法发现误报和噪声 | 同时加入合法反例和无关改动 |

## 八、面试总结话术

> 我把 Codex 当作能操作仓库的工程协作者，而不是自动答案生成器。首先我会给它清晰的目标、范围、约束、验收标准和验证命令，让它读取适用的 `AGENTS.md`、现有代码和测试，避免脱离仓库猜实现。执行时坚持最小改动，涉及删除、依赖升级、外部写入、生产环境和敏感数据时设置明确的权限边界。验证上先跑最相关的单测，再逐步扩大到类型检查、lint、集成测试、E2E 和生产构建，同时检查失败路径、兼容性及最终 diff。没有实际运行的测试不会描述为通过。对于 Codex 自身，我会用应触发样例、合法反例和无关样例建立回归集，关注检出率、误报率和建议可执行性。最后仍由 CI、分支保护和人工评审提供硬性质量门槛。
