# 浏览器调试与前端性能实战

## 1. 面试开场：页面慢，你怎么排查？

> 我会先区分是首屏加载慢、操作响应慢，还是使用一段时间后越来越卡。首屏看 FCP、LCP、TTFB 和 Network 瀑布图，确定慢在接口、资源发现、下载还是渲染；交互看 INP 和 Performance，定位长任务、组件更新和布局；持续变慢则用 Memory 对比堆快照，检查监听器、定时器和未释放的 DOM。定位后再分别处理 Webpack 分包、HTTP 缓存、图片加载和 React/Vue 更新，最后在相同设备、网络和缓存条件下复测。

面试里要讲清楚：**看到了什么证据，为什么采用这项优化，怎么证明有效。** “用了懒加载、加了缓存”只能说明做过配置，不能说明解决了瓶颈。

## 2. 性能指标：先确定要解决什么问题

### 2.1 FCP 和 LCP 有什么区别？

面试常用回答：**FCP 衡量页面什么时候开始显示内容，LCP 衡量页面主要内容什么时候显示出来。**

- **FCP（First Contentful Paint，首次内容绘制）**：从页面开始加载到首次绘制文本、图片等内容的时间，反映用户什么时候开始看到内容。
- **LCP（Largest Contentful Paint，最大内容绘制）**：从页面开始加载到视口内最大的符合条件的图片、文本块等内容完成绘制的时间，反映主要内容的呈现速度。

例如：页面先显示标题，随后显示占据首屏大部分面积的主图。标题首次出现时可能触发 FCP，主图绘制完成时可能成为 LCP。LCP 按元素的可见面积判断，并不是所有内容加载完成的时间。

骨架屏也要看实际绘制内容：文字、图片可能触发 FCP，单纯的背景色块不一定触发。骨架屏先出现只能改善等待感受，不能据此判断业务内容加载快；LCP 候选元素还可能随着更大的内容出现而更新。

### 2.2 常用指标与判断依据

| 指标 | 衡量什么 | 良好标准 | 排查方向 |
| --- | --- | --- | --- |
| FCP | 首次内容出现 | ≤ 1.8 秒 | HTML 响应、阻塞样式、字体和首屏脚本 |
| LCP | 最大符合条件的可见内容呈现 | ≤ 2.5 秒 | TTFB、LCP 资源发现与下载、元素渲染延迟 |
| INP | 页面生命周期内代表性的较差交互延迟 | ≤ 200 毫秒 | 输入延迟、事件处理、下一帧呈现延迟 |
| CLS | 页面生命周期内最严重的一组意外布局偏移 | ≤ 0.1（无单位） | 图片尺寸、动态插入内容、字体替换 |
| TTFB | 导航开始到收到响应首字节的时间 | ≤ 800 毫秒 | 重定向、连接、CDN、源站处理等 |

Core Web Vitals 是 LCP、INP、CLS；FCP 和 TTFB 是辅助诊断指标。常用“良好”阈值为 LCP 不超过 2.5 秒、INP 不超过 200 毫秒、CLS 不超过 0.1，应按真实访问的第 75 百分位，并区分移动端与桌面端评估。

INP 不是所有点击耗时的平均值，也不包含接口返回前的整个业务等待时间；一次点击先画出 loading，即使数据仍未返回，也可能很快完成这次交互的呈现。CLS 按会话窗口统计，通常不会计入紧随用户输入的预期偏移，因此不能简单把所有位移相加。

### 2.3 实验室结果与真实用户数据

- Lighthouse 适合受控环境下发现问题；单次分数会波动，不能代表所有用户体验。
- 真实用户监控可使用 `web-vitals` 收集 FCP、LCP、CLS、INP、TTFB，按路由、版本、设备和网络分组。上报内容应避免用户敏感数据。
- Lighthouse 的 TBT 可辅助判断加载阶段主线程阻塞，但不能替代真实交互的 INP。
- 对比时固定浏览器、设备、网络、CPU 降速及测试操作，重复测量；分别记录冷缓存与热缓存。DevTools 的 Disable cache 主要影响浏览器 HTTP 缓存，不会自动清空 CDN 或 Service Worker 缓存。

### 2.4 web-vitals：如何采集真实用户性能？

`web-vitals` 是 Google 提供的轻量级 JavaScript 性能监控库，主要用于采集真实用户访问网站时的性能指标，也就是 **RUM（Real User Monitoring，真实用户监控）**。它基于浏览器性能 API 计算指标，适合 React、Next.js 等项目，也可以用于 Vue 或原生 JavaScript 项目。

它可以采集上表中的 **FCP、LCP、CLS、INP、TTFB**，但其中只有 **LCP、INP、CLS 是当前三大 Core Web Vitals**，分别对应加载速度、交互响应和视觉稳定性。FCP 和 TTFB 用于辅助定位问题；使用这个库并不代表五项指标都属于 Core Web Vitals。

```js
// 安装 web-vitals 后，在浏览器端入口初始化一次
import { onFCP, onLCP, onCLS, onINP, onTTFB } from 'web-vitals';

function reportMetric({ name, value, rating, id }) {
  // 演示采集结果；生产环境对接自己的监控上报接口
  console.log({ name, value, rating, id });
}

onFCP(reportMetric);
onLCP(reportMetric);
onCLS(reportMetric);
onINP(reportMetric);
onTTFB(reportMetric);
```

`value` 中的时间指标以毫秒为单位，CLS 没有单位；`rating` 表示 `good`、`needs-improvement` 或 `poor`，`id` 用于标识一次指标记录。库负责测量并调用回调，数据存储、聚合和告警需要接入自己的监控平台；真实用户没有发生符合条件的交互时，也不一定会产生 INP。

React 项目应在客户端入口统一注册，避免在组件每次渲染时重复注册。Next.js 也提供 `next/web-vitals` 的 `useReportWebVitals` Hook，可在客户端组件中接收指标；同一批指标选择一种采集入口，避免重复上报。普通 SPA 路由切换不会自动为每个路由重置全部页面指标，因此不能把导航级数据直接当作每个子路由的独立测量结果。

面试常用回答：**我用 web-vitals 采集真实用户的五项性能指标，重点看 LCP、INP、CLS 三大 Core Web Vitals，再按设备、版本等维度统计第 75 百分位。发现异常后结合 DevTools 定位原因，优化发布后再用真实用户数据验证。**

### 2.5 怎么优化 FCP：让第一份内容尽早画出来

FCP 的重点是缩短“拿到 HTML → 解析出内容 → 满足绘制条件”的关键路径。先看 TTFB，再查阻塞首屏的 CSS、JS 和字体。

1. **让 HTML 更早到达**：减少重定向，优化服务端处理；可缓存页面使用 CDN、页面缓存或静态生成。个性化 HTML 要正确设置缓存范围，不能直接共享缓存。
2. **减少阻塞渲染的 CSS**：按页面拆分样式，删除确认无用的 CSS，必要时内联少量关键样式。避免把所有 CSS 都内联，导致 HTML 膨胀；非关键样式延后加载时也要避免无样式闪烁。
3. **减少首屏 JS 下载与执行**：Webpack 按路由和功能分包，延迟图表、编辑器及第三方脚本；普通外部脚本按依赖选择 `defer` 或 `async`，避免阻塞 HTML 解析。分包后仍要用 Performance 检查执行长任务。
4. **让内容不必等客户端初始化**：React、Vue 的纯客户端页面可能要等 JS 和接口完成才有业务内容，可根据页面特点采用 SSR、SSG 或预渲染。Next.js 首屏内容尽量直接由服务端输出，避免全部放进 `useEffect` 请求后再显示；同时检查 SSR 是否增加了 TTFB。
5. **避免字体挡住文字**：字体裁剪、使用 WOFF2，按需设置 `font-display: swap` 或 `optional`，让回退字体先显示；只预加载首屏确实需要的字体，并留意替换字体带来的布局偏移。

**验证方式**：用 Network 确认 HTML 和阻塞资源的耗时，用 Performance 截图确认第一份内容更早出现，再用真实用户 FCP 的第 75 百分位验证。加骨架屏可能让 FCP 提前，但仍需检查主要内容是否同样变快。

### 2.6 怎么优化 LCP：让首屏主要内容尽早显示

先在 Performance 或 Lighthouse 中确认实际的 LCP 元素。**LCP 可能是主图，也可能是文本块**，不能一律只做图片压缩。对于以图片为 LCP 的页面，可按四段耗时定位：

| 阶段 | 常见原因 | 优化措施 |
| --- | --- | --- |
| TTFB | HTML 响应晚 | 优化服务端、CDN 和缓存，减少重定向 |
| 资源加载延迟 | 图片等 JS、接口或 CSS 才被发现 | 在初始 HTML 输出图片地址；必要时精准 preload；对关键图设置 `fetchpriority="high"` |
| 资源加载时长 | 图片过大、尺寸不匹配、网络慢 | 使用 AVIF/WebP、合理压缩，通过 `srcset` / `sizes` 选择合适尺寸，结合 CDN 与缓存 |
| 元素渲染延迟 | 图片已下载，但主线程忙或元素仍被隐藏 | 减少长任务和首屏组件工作量，移除等待 hydration、动画或整页接口完成才显示的限制 |

- **首屏 LCP 图不要懒加载**：避免 `loading="lazy"`，让浏览器尽早发现和请求；屏外图片再懒加载。`fetchpriority` 是调度提示，不要给所有图片都设为高优先级。
- **preload 要对准实际资源**：适合 CSS 背景图等发现较晚的关键资源；响应式图片要匹配实际选图条件，避免预加载了另一张图片，浪费带宽。
- **React / Vue 先呈现关键内容**：首屏主图、标题不要依赖非关键图表、弹窗或推荐接口全部完成；把非关键组件异步加载，避免一次渲染超大列表。
- **如果 LCP 是文字**：优先检查字体阻塞、关键 CSS、服务端内容输出和主线程工作量；图片压缩通常无法直接解决这类瓶颈。

**验证方式**：对比同一页面、相同测试条件下的 LCP 元素及四段耗时，确认瓶颈是否缩短；优化后候选元素可能变化，需要重新检查。最终用真实用户 LCP 的第 75 百分位验证，而不是只看图片体积或 Lighthouse 单次分数。

### 2.7 面试总结：FCP 和 LCP 优化分别怎么说？

> FCP 优化关注“尽早显示第一份内容”：先降低 TTFB，再减少阻塞 CSS 和 JS，优化字体，必要时用 SSR 或静态生成，让内容不用等客户端初始化。LCP 优化关注“尽早显示主要内容”：先找到实际 LCP 元素，如果是主图，就从响应时间、资源发现、下载和渲染四个阶段排查，让图片在 HTML 中尽早被发现，避免懒加载，合理设置优先级、格式和尺寸，同时减少主线程阻塞；如果是文本，就重点查字体和渲染。最后结合 DevTools 和 web-vitals 验证，FCP 变好不代表 LCP 一定变好。

## 3. Chrome DevTools：从现象找到证据

### 3.1 Network：资源为什么晚到？

先打开 Network，保留需要的日志，再录制一次完整导航。按资源类型、大小和耗时筛选，但不要只看最慢的一行。

1. **Waterfall**：看关键请求何时开始，是否存在“脚本下载 → 执行 → 接口 → 图片”的串行链。
2. **Timing**：区分 Queueing/Stalled、DNS、连接/TLS、Waiting for server response（TTFB）和 Content Download。连接复用时不一定出现握手阶段。
3. **Initiator**：找出请求由 HTML、CSS 还是哪段 JS 发起；图片很小却很晚开始，可能是发现太晚。
4. **Size / Headers**：区分传输量与解压后的资源大小，确认 `Content-Encoding`、缓存响应头、状态码以及 memory/disk cache 标记。
5. **Priority**：检查关键图是否与非关键资源争抢带宽；优先级提示是否有用，仍以实际调度和指标为准。

TTFB 高不能直接断言“后端代码慢”：请求可能经过代理、CDN 和网络往返，需要结合服务端日志或 `Server-Timing`。下载慢则检查传输体积和带宽，排队慢则检查连接、优先级与并发竞争。

### 3.2 Performance：资源到了，为什么还没显示？

录制页面加载或一次明确操作，结合截图、主线程时间线与调用栈看：

- **长任务**：单个任务超过 50 毫秒，可能延迟输入和绘制。用 Bottom-up 找累计耗时热点，用 Call tree 看调用路径。
- **脚本执行**：检查第三方 SDK、JSON 处理、大循环和框架初始化；JS 下载快，不代表解析执行便宜。
- **样式与布局**：查看 Recalculate Style、Layout，以及强制同步布局提示。循环里交替写样式、读 `offsetHeight` 等布局信息容易触发布局抖动。
- **绘制与布局偏移**：定位 LCP 元素和布局偏移记录，确认慢在资源加载还是元素展示；用 Rendering 的 Paint flashing 辅助观察重绘范围。

优化布局读写时，先批量读取，再批量写入。动画优先考虑 `transform`、`opacity`，但复杂合成层仍有内存和合成成本。`requestAnimationFrame` 只负责在合适时机执行，不能自动消除回流或把大计算移出主线程。

### 3.3 Coverage：哪些代码这次没有用到？

从命令菜单打开 Coverage，重新加载并操作目标功能，观察 JS/CSS 的未使用比例，再回到源模块分析原因。它能提示首屏不需要的大依赖，但“本次未执行”不等于“永远无用”，不能按红色区域直接删除功能代码。

### 3.4 Memory：为什么越用越卡？

1. 打开页面，等待初始化稳定，必要时手动触发 GC，记录基线堆快照。
2. 多次执行“进入详情 → 返回列表”等相同操作，再触发 GC 并拍快照。
3. 用 Comparison 检查持续增长的对象、Detached DOM 和 Retained Size，通过 Retainers 查到保留引用的来源。
4. 清理对应监听器、定时器、订阅或缓存，再重复同样操作确认增长是否收敛。

一次内存上升不足以证明泄漏，缓存和延迟 GC 都可能造成增长。Detached DOM 也要结合引用链判断；DevTools 控制台保存的对象引用可能干扰结果。

## 4. Webpack：首屏包大、分包后仍然慢

### 4.1 先查哪些东西进了首屏

用生产构建的 stats 和 bundle analyzer 检查模块组成，再与 Network 的初始 chunk 对应。重点找图表、编辑器、整套 UI 库、重复版本依赖和未使用语言包。

- 原始体积用于观察代码组成；gzip/Brotli 后体积用于估计传输成本，两者都不能直接代表执行时间。
- 包重复时看依赖树和版本约束，在兼容前提下收敛版本。
- 同样配置下比较修改前后产物及首屏实际请求，不能只看构建日志的总大小。

### 4.2 动态 import 与 splitChunks 分别做什么？

`import()` 提供异步加载边界；调用时机决定何时开始加载。`splitChunks` 处理模块复用和 chunk 拆分，不会替你决定业务什么时候需要某个功能。

```jsx
import { lazy, Suspense } from 'react';

const ChartPanel = lazy(() => import('./ChartPanel'));

export function Report({ showChart }) {
  return showChart ? (
    <Suspense fallback={<p>图表加载中…</p>}>
      <ChartPanel />
    </Suspense>
  ) : null;
}
```

组件需要渲染时才触发加载。若模块还被其他首屏代码同步引用，或框架进行了预取，就不能假定它一定不会提前下载。加载失败需要 Error Boundary 提供提示和重试/刷新入口，`Suspense` 只处理等待状态。

```js
// 独立 Webpack 5 配置片段，不直接覆盖框架的构建配置
module.exports = {
  mode: 'production',
  output: { filename: '[name].[contenthash].js' },
  optimization: {
    runtimeChunk: 'single',
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        shared: {
          minChunks: 2,
          reuseExistingChunk: true,
        },
      },
    },
  },
};
```

是否提取公共包要结合复用率与缓存判断：一个巨大的 vendors 包可能让首屏下载大量无关模块；过碎的 chunk 又可能增加请求和依赖调度成本。以首次访问和跨页面访问结果验证拆分边界。

### 4.3 Tree Shaking、压缩和缓存

- **Tree Shaking**：利用 ESM 的静态结构分析未使用导出，再由生产优化删除代码。需保留 ESM，正确声明副作用，避免把必须执行的初始化或 CSS 错误标成可删除。
- **代码压缩**：减少语法体积、删除可判定的无用代码；不能保证任意 CommonJS 依赖都能精准裁剪。
- **gzip/Brotli**：由服务器或 CDN 协商提供压缩响应，检查 `Content-Encoding`；Webpack 生成预压缩文件后也需要服务器正确分发。
- **contenthash**：内容变更时变更资源 URL，与长期 HTTP 缓存配合；HTML 更新时应引用新 URL，发布时保留旧资源以支持已打开页面的异步加载。
- **构建缓存**：Webpack 文件系统缓存加速开发/构建，通常不会直接改善用户运行时首屏。

**追问：包小了为什么还卡？** 看 Performance。包大小下降不一定减少启动时计算；大循环、同步解析、第三方初始化仍可能阻塞主线程。可以延迟非关键初始化、分片执行，适合脱离 DOM 的大计算可用 Web Worker，并考虑通信和序列化成本。

## 5. HTTP：接口慢、资源重复下载与缓存失效

### 5.1 按 Timing 对症处理

| 证据 | 可能原因 | 优化与验证 |
| --- | --- | --- |
| 请求很晚才发起 | JS 执行后才发现资源、接口串行 | 提前暴露关键资源；独立接口并行；确认瀑布链缩短 |
| DNS / TLS 较长 | 新域名、连接建立成本 | 减少无意义域名；对关键跨域源谨慎 preconnect |
| TTFB 高 | 网络、CDN miss、源站处理慢 | 分层查看 CDN 与服务端耗时，验证命中率和响应时间 |
| Content Download 长 | 资源大、带宽低 | 压缩、裁剪、分页；比较实际传输字节 |
| 每次都下载相同资源 | 缓存策略、URL 或响应变化 | 检查请求/响应头、缓存层和构建 hash |

依赖上一步结果的请求不能机械并行；减少不必要串行时，也要保留错误处理、取消过期请求及接口限流边界。

### 5.2 强缓存与 304

```http
# 带内容 hash 的公开静态资源
Cache-Control: public, max-age=31536000, immutable

# HTML：允许存储，每次复用前校验
Cache-Control: no-cache
ETag: "html-version-42"

# 敏感响应：不存储
Cache-Control: no-store
```

以上是不同响应的示例，不能把三组头同时配置到同一资源。

强缓存仍新鲜时，浏览器可直接复用本地资源。需要重新验证且有验证器时，请求可携带 `If-None-Match` 或 `If-Modified-Since`；服务端确认未变后返回 304，浏览器复用本地响应体。304 仍有请求往返与校验成本。`no-cache` 允许存储但要求复用前校验，`no-store` 才是不存储。

HTML 常使用协商缓存或较短有效期；带 hash 的资源适合长期缓存。API 需要按业务决定新鲜度，个性化响应不应被共享 CDN 意外复用，可按需求使用 `private` 或 `no-store`，不能统一设置一年缓存。

### 5.3 浏览器、CDN、Service Worker 缓存怎么区分？

- **浏览器 HTTP 缓存**：看 Network 的 memory/disk cache、状态码和缓存响应头。
- **CDN 缓存**：看供应商命中标记、`Age` 等响应头并结合 CDN 日志；浏览器收到 200 也可能是 CDN 命中。
- **Service Worker / Cache Storage**：在 Application 面板检查注册与缓存。它可以拦截请求并返回缓存，但缓存 key、有效期和更新策略需由实现管理。

排查“发版后还是旧页面”时，先确认响应到底来自哪一层，再检查 HTML、新资源 URL、CDN 刷新和 Service Worker 更新。直接让用户清空所有缓存不能替代定位。

### 5.4 HTTP/2 能解决一切请求问题吗？

HTTP/2 多路复用和头部压缩能改善 HTTP/1.1 的部分连接限制，但仍受 TCP 丢包、带宽、服务端和请求依赖影响。HTTP/3 基于 QUIC，改善不同 stream 间的传输层队头阻塞，也不能消除业务串行与大资源成本。

**追问：请求数越少越好吗？** 需要同时考虑总字节、优先级、缓存粒度和依赖深度。将全部业务合并成一个大包，可能降低请求数却拖慢首屏。

## 6. 图片处理：LCP 大图与多图片列表

### 6.1 首屏大图为什么慢？

按顺序检查：HTML 是否及时返回 → 图片何时被发现 → 下载何时完成 → 为什么下载后还没画出来。

常见问题包括：CSS 背景图等样式下载后才被发现；接口返回后才生成图片 URL；下载了远大于展示尺寸的原图；图片已到但被 loading 状态、动画或主线程长任务挡住。

### 6.2 按展示需求提供资源

- 按展示尺寸及设备像素比生成不同尺寸，不要用数千像素原图展示小缩略图。
- 比较 WebP、AVIF 与原格式的实际体积、画质、编码成本和目标浏览器支持；必要时提供回退格式。
- 用 `srcset` 和 `sizes` 描述候选资源与实际布局宽度，在 Network 验证浏览器选中的图片。
- 指定 `width`/`height` 或稳定宽高比，提前预留空间，避免加载后把下方内容顶开。

```html
<picture>
  <source
    type="image/avif"
    srcset="/hero-640.avif 640w, /hero-1280.avif 1280w"
    sizes="(max-width: 640px) 100vw, 640px"
  />
  <img
    src="/hero-1280.jpg"
    srcset="/hero-640.jpg 640w, /hero-1280.jpg 1280w"
    sizes="(max-width: 640px) 100vw, 640px"
    width="1280"
    height="720"
    fetchpriority="high"
    alt="活动主图"
    style="display: block; width: 100%; max-width: 640px; height: auto;"
  />
</picture>
```

示例假设桌面展示宽度最多为 640px，实际项目应按真实布局和目标像素比提供候选尺寸。HTML 的属性是 `fetchpriority`，React JSX 使用 `fetchPriority`。

### 6.3 首屏图及时加载，屏外图按需加载

LCP 图片通常不设置 `loading="lazy"`。优先让浏览器能从初始 HTML 发现它，只有确实重要的资源才考虑高优先级。对于必须晚发现的关键图，可谨慎 preload；响应式图片要匹配 `imagesrcset`/`imagesizes`，避免预加载地址与最终选图不一致。

```html
<!-- 屏外列表图：延后请求，并预留比例 -->
<img
  src="/product-480.webp"
  width="480"
  height="360"
  loading="lazy"
  decoding="async"
  alt="商品预览"
/>
```

`fetchpriority` 是调度提示，不会减少图片字节；preload 太多会争抢带宽。`decoding="async"` 是解码提示，不会减少解码总成本，也不能保证某个绘制时机。下载文件小并不代表内存小，高分辨率图片解码后仍可能占用较大内存。

### 6.4 图片懒加载、分页、虚拟列表有什么区别？

| 手段 | 解决的问题 | 不能替代的部分 |
| --- | --- | --- |
| 图片懒加载 / IntersectionObserver | 延后屏外资源请求 | 不会自动减少已挂载 DOM |
| 分页 / 无限滚动 | 分批获取和追加数据 | 持续追加仍会积累 DOM 和内存 |
| 虚拟列表 | 只挂载可见区及缓冲区的项 | 仍需控制图片尺寸、请求和数据量 |

长列表优先根据测量结果选方案。不等高卡片需要处理高度测量、占位、滚动位置和图片加载后的尺寸变化，不能只截取数组而不保留整体滚动空间。

## 7. React：组件为什么频繁更新？

### 7.1 先用 Profiler 找到昂贵的提交

用 React DevTools Profiler 录制一次操作，看哪些组件参与更新、耗时集中在哪里；在支持的设置中记录更新原因，并对照 props、state 与 context。再结合浏览器 Performance，区分组件计算与真实 DOM 布局/绘制成本。

开发环境的检查和 StrictMode 可能额外执行渲染或 effect，不能直接拿开发耗时当上线结果。需要精确分析生产行为时使用支持 profiling 的构建，并在相同条件下复测。

### 7.2 按原因优化，不给所有组件加 memo

- 输入状态只影响局部区域时，将状态下沉，避免每次输入都让整页参与渲染。
- 父组件更新带动昂贵子组件，且子组件 props 经常相同，才考虑 `memo`；它不能阻止子组件自己的 state 或订阅的 context 更新。
- `useMemo` 缓存昂贵计算结果，`useCallback` 缓存函数引用；依赖变化仍会重新计算，缓存比较也有成本。
- 对传给记忆化组件的对象、数组和回调关注引用稳定性，不要随意省略依赖制造旧闭包。
- 使用稳定业务 ID 作为列表 key；key 主要保证身份匹配，不能自动避免所有渲染。
- 大列表考虑虚拟化，非首屏模块使用懒加载。`startTransition` / `useDeferredValue` 可改善更新调度，但不会减少计算总量，也不会自动把同步大循环变成后台任务。

```jsx
import { memo, useMemo } from 'react';

const ProductList = memo(function ProductList({ items }) {
  return <ul>{items.map(item => <li key={item.id}>{item.name}</li>)}</ul>;
});

export function ProductPanel({ products, query, theme }) {
  const visible = useMemo(
    () => products.filter(item => item.name.includes(query)),
    [products, query],
  );
  return <section className={theme}><ProductList items={visible} /></section>;
}
```

在 `products`、`query` 不变且引用稳定时，只切换 theme 可让列表跳过一次无意义渲染。过滤本来很便宜、列表很小时，这种缓存未必值得；应通过 Profiler 验证。不要直接修改 `products` 后继续使用同一引用，否则缓存和更新判断可能失效。

### 7.3 effect 清理：离开页面后还在执行吗？

```jsx
import { useEffect, useState } from 'react';

export function ViewportWidth() {
  const [width, setWidth] = useState(0);
  useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);
    handleResize();
    window.addEventListener('resize', handleResize);
    return () => window.removeEventListener('resize', handleResize);
  }, []);
  return <span>{width}px</span>;
}
```

监听器移除时要匹配原函数引用和 capture 配置。定时器、WebSocket 和订阅同样需要对应清理；effect 内发起请求可用 `AbortController` 取消过期请求，并正确处理取消异常，避免旧响应覆盖新状态。真实高频 resize 还应按需要节流。

## 8. Vue：响应式更新、组件缓存与副作用

### 8.1 用工具确认更新范围

用 Vue DevTools 检查组件状态和更新，结合浏览器 Performance 录制具体交互。开发环境可按需启用 `app.config.performance` 输出 Vue 性能标记；组件耗时之外仍要检查布局、绘制和脚本长任务。

Vue 具有响应式依赖追踪，不代表所有更新都天然便宜：模板里反复排序、深层 watch、大列表和昂贵子组件仍会卡顿。

### 8.2 常见优化选择

- 对由响应式数据推导的值使用 `computed`，避免模板中重复执行昂贵方法；计算属性应保持纯计算。
- 保持 props 稳定。例如给每项传 `active` 布尔值，而不是让所有项都依赖变化的 `activeId`；是否有收益仍看组件实际更新。
- `v-if` 控制挂载与卸载，切换成本较高；`v-show` 初次就渲染，只切换显示。隐藏元素仍占内存，相关逻辑也不会因此自动停止。
- 深层 watch 会遍历嵌套结构，应缩小监听目标；超大且按不可变方式更新的数据可评估 `shallowRef`，同时遵守其只追踪根引用的约定。
- 非首屏组件使用 `defineAsyncComponent`，路由使用动态导入；大列表仍需要分页或虚拟化。

```vue
<script setup>
import { computed, defineAsyncComponent, ref } from 'vue';

const props = defineProps({ products: { type: Array, default: () => [] } });
const query = ref('');
const showChart = ref(false);
const visible = computed(() =>
  props.products.filter(item => item.name.includes(query.value)),
);
const ChartPanel = defineAsyncComponent(() => import('./ChartPanel.vue'));
</script>

<template>
  <input v-model="query" placeholder="搜索商品" />
  <ul><li v-for="item in visible" :key="item.id">{{ item.name }}</li></ul>
  <button @click="showChart = !showChart">切换图表</button>
  <ChartPanel v-if="showChart" />
</template>
```

异步加载的错误、超时和等待状态可通过 `defineAsyncComponent` 的选项配置。`computed` 只减少不必要的重新计算，不会让首次大数据过滤自动变便宜。

### 8.3 KeepAlive 缓存后为什么定时器还在跑？

KeepAlive 停用时组件被缓存，并未卸载，因此不能只依靠 `onUnmounted` 停止轮询。应在激活时启动，在停用和最终卸载时清理，且避免重复注册。

```vue
<script setup>
import { onActivated, onDeactivated, onMounted, onUnmounted } from 'vue';

let timer;
function refresh() {
  // 替换为业务刷新逻辑；异步请求还需处理并发与取消
}
function stop() {
  if (timer !== undefined) clearInterval(timer);
  timer = undefined;
}
function start() {
  stop();
  timer = setInterval(refresh, 30000);
}

onMounted(start);
onActivated(start);
onDeactivated(stop);
onUnmounted(stop);
</script>
```

此示例兼容普通挂载与 KeepAlive：首次挂载时两个启动钩子可能先后运行，但 `start` 先清理，确保只有一个计时器。真实接口若耗时不定，可用请求完成后再安排下一次的方式避免轮询重叠。还要按业务考虑页面进入后台时暂停刷新。

KeepAlive 的 `max` 可限制缓存实例数量，但不能替代组件副作用清理；React 中通过隐藏而不卸载实现的页面缓存，也需要显式管理激活/停用状态。

## 9. 综合案例：商品页首屏慢，筛选时卡顿

以下是假设场景，用于练习排查表达，不代表已经测得的项目结果。

页面包含首屏 Banner、商品列表和按需查看的图表。用户反馈首次打开慢、输入筛选词卡、反复进入退出后内存增加。

| 阶段 | 发现的证据 | 采取的措施 | 复测依据 |
| --- | --- | --- | --- |
| 首屏 JS | 图表库位于初始 chunk，启动执行耗时明显 | 图表按交互动态导入，分析重复依赖 | 初始 chunk 与传输量、脚本耗时 |
| Banner | 图片由列表接口返回后才发现，且下载原图 | 尽可能初始暴露关键 URL，提供响应式尺寸 | 请求开始时间、传输字节、LCP |
| 缓存 | 相同 hash 资源反复下载 | 修正静态资源缓存，单独管理 HTML | 热访问缓存命中及内容更新正确性 |
| 筛选 | 每次输入触发大列表计算和更新 | 缩小状态范围，按测量缓存计算，虚拟化 | Profiler、长任务和交互延迟 |
| 返回页面 | 定时器与组件相关引用持续增长 | 修正卸载/停用清理，限制无界缓存 | 相同操作与 GC 后堆增长是否收敛 |

执行时一次优先验证一个明确假设，保存改动前后的相同条件记录。没有真实测量就说“预期减少首屏下载，待复测验证”，不要编造“提升 80%”。同时验证功能不退化：异步模块加载失败有提示、缓存更新后能看到新内容、列表滚动及筛选仍正确。

## 10. 面试速查与高频追问

| 现象 | 优先工具 | 关键检查 | 验证目标 |
| --- | --- | --- | --- |
| 首屏长时间空白 | Network、Performance | HTML、阻塞 CSS、启动 JS | FCP、LCP 和主线程耗时 |
| 标题快但主图慢 | Network、LCP 记录 | 图片发现、优先级、体积、渲染延迟 | LCP 及其阶段耗时 |
| 接口慢 | Network Timing、服务端日志 | 串行、TTFB、下载、取消与重试 | 请求耗时和业务等待 |
| 点击或输入卡 | Performance、框架 Profiler | 长任务、组件计算、布局 | INP、交互 trace |
| 页面跳动 | Performance 布局偏移记录 | 图片占位、插入内容、字体 | CLS、视觉稳定性 |
| 使用越久越慢 | Memory、Application | 引用链、定时器、订阅、缓存 | 重复操作后内存收敛 |

### 为什么 FCP 很好，LCP 仍然差？

小标题可能很快出现，但主图等待接口、下载太大，或者已加载却被脚本阻塞绘制。应查看 LCP 元素及资源链，不能只继续优化标题。

### preload、prefetch、preconnect 有什么区别？

preload 提前请求当前页面明确需要的资源；prefetch 提示为未来可能的导航准备资源，是否执行受浏览器策略影响；preconnect 提前建立到目标源的连接，不会下载具体业务资源。都应按真实关键路径选择，不能批量添加。

### 防抖能否替代渲染优化？

防抖可减少搜索请求或计算次数，但增加等待，也不能解决一次执行就很慢的问题。应同时处理取消旧请求、响应顺序和昂贵计算；输入反馈本身要及时。

### React memo 和 Vue computed 是一回事吗？

不是。React `memo` 主要根据 props 比较跳过组件渲染，Vue `computed` 主要缓存响应式派生值；它更接近 React `useMemo` 的使用目的，但依赖收集机制不同。是否使用要看具体瓶颈，不能按 API 名字机械套用。

### 怎样证明优化确实有效？

给出一致条件下的前后数据和 trace：加载看关键资源与 LCP，交互看任务和 INP，内存看重复操作后的保留对象。再通过真实用户数据确认不同设备、路由与版本没有回退，而不是只展示一次 Lighthouse 高分。
