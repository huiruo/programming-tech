# WebSocket / Socket.IO 面试复盘

## 30 秒项目介绍

项目使用 NestJS Gateway + Socket.IO 服务端和 `socket.io-client` 客户端，强制走 WebSocket transport。Socket 不负责替代数据库：HTTP/Service 负责鉴权、落库、权限校验和查询历史；Socket.IO 只负责把已确认的状态变化实时推给正确的用户或房间。这一点让实时链路可以断线重连，而正确性仍由数据库保证。

## 心跳怎么实现？

### 可以直接这样回答

我们没有自己定义业务层 `heartbeat` 事件，而是使用 Socket.IO/Engine.IO 内置的 ping/pong 心跳。服务端和客户端都强制 `transports: ['websocket']`，底层会周期性发送 ping，客户端自动 pong；在一个 ping 超时窗口内没有收到 pong，Socket.IO 判定连接失效并触发 `disconnect`。客户端在断开后按 `reconnectionDelay: 5000` 重连，最多尝试 360 次；重连成功后恢复事件监听和普通频道订阅。

服务端打开了 `connectionStateRecovery`，允许 60 秒内断线恢复 Socket.IO 的连接状态；同时在握手中重新执行认证中间件（`skipMiddlewares: false`）。不过群聊房间是例外：恢复时会清理 `group:*` 和非当前用户的 `user:*` 房间，客户端要重新鉴权后订阅，历史消息再通过 HTTP 补齐。这样避免“已被移出群的用户”因为恢复旧房间而继续收到消息。

### 追问：为什么不手写心跳？

- 传输层存活检测交给 Socket.IO，避免重复实现 ping/pong、超时、网络抖动和重连状态机。
- 业务心跳只在需要上报业务状态时才补充，例如 runner 的任务进度或机器人运行状态；它不能代替连接层心跳。
- 当前代码没有显式配置 `pingInterval` / `pingTimeout`，使用 Socket.IO 默认值。若面试官追问 SLA，我会说线上会根据移动网络和代理的实际表现配置，并监控断连率、重连率、心跳超时和重连耗时。

### 断线处理的闭环

`disconnect` 时服务端从 `activeUsers` 移除连接，并按 `socket.id` 注销机器人连接管理器；`connect_error`、`disconnect`、`connect` 都会更新客户端连接状态并通知订阅者。普通频道在客户端 `Set` 中维护期望订阅，重连后 `rejoinChannels()` 批量重新加入。群组不放进这个自动恢复集合，必须走受鉴权保护的 `group:join`。

## 群聊怎么实现？

### 领域模型：一个群 = 一条业务 Channel 记录 + 一个实时 Room

是的，线上“量见会员反馈群”就是一条 `channel` 记录：`id = 1`、`isGroup/group = 1`；它对应的实时订阅房间固定命名为 `group:1`。两者不是同一个东西：

- `channel` 是持久化的业务实体，保存群资料、成员关系和消息历史，也是权限校验与 HTTP 接口使用的群 ID。
- `group:1` 是 Socket.IO 运行时 room，只保存当前在线且已获授权的订阅者，用来定向实时广播；它不保存聊天记录，也不能作为权限事实来源。

因此创建群时创建业务 channel；用户进入这个群页时调用 `group:join({ channelId: '1' })`，服务端校验成员关系后让 Socket 加入 `group:1`；发送消息时仍以 `channelId = 1` 走 HTTP 写库，成功后再广播至 `group:1`。断线后 room 可以重建，历史消息则始终从数据库按 channel ID 补拉。

注意：裸房间名 `1` 与 `group:1` 是两个不同的 Socket.IO room。项目的行情普通频道也曾使用裸数字 `1`，所以群房间加 `group:` 前缀是必要的命名空间隔离；群消息绝不能广播到裸 `1`，否则订阅行情频道的用户可能收到无关事件。通用频道接口也会识别数据库中 `id = 1` 是群并拒绝用它发消息，强制改走群 API。

### Socket.IO 原理：使用 Room（房间）做群广播

群聊实时层采用 Socket.IO 的 **Room** 设计，不是 Namespace，也不是“一个群创建一条 WebSocket 连接”。一个客户端只维持一条 Socket.IO 连接，但可以同时加入多个 room；服务端 Adapter 维护 `room -> socketId 集合` 的订阅关系。这里的映射是：

```text
群业务 ID 1 ──> Socket.IO room "group:1" ──> [socket-A, socket-B, socket-C]
用户多开页面 ──> 同时有多个 socketId，都可加入 "group:1"
```

核心调用及含义：

- 加入：`client.join('group:1')`，把当前 socketId 注册进 room。
- 广播：`server.to('group:1').emit('group:message-created', data)`，Adapter 只把事件投递给 room 内的在线 socket。
- 离开：`client.leave('group:1')`；踢人时先取得该用户私有 room `user:<userId>` 中的全部 socket，再逐个 leave，保证多标签页/多设备同时退群。
- 断连：Socket.IO 自动从 room 移除该 socket；恢复或重新进入页面时，仍需再次做成员鉴权才允许 join。

`Namespace`（例如 `/chat`）更适合隔离一整套连接协议、中间件或租户；本项目所有实时能力共用默认 namespace `/`，而行情、MQ、群、机器人等“订阅集合”采用 room 区分。这样连接和鉴权开销更低，也可以一次广播给一个群的所有在线成员。

### 关键设计：HTTP 写库，Socket 广播

发送群消息的流程是：

1. 前端通过 HTTP `POST /api/groups/:id/messages` 提交消息和 `requestId`，不允许直接用 Socket 写群消息。
2. `GroupService.send` 在数据库事务中验证账号有效、群存在、用户仍是成员，并完成持久化/幂等处理。
3. 只有 `created` 为真时，Controller 调用 `gateway.emitGroup(id, 'group:message-created', message)`。
4. Gateway 向 `group:<channelId>` 房间广播；客户端监听 `group:message-created` 后刷新本地会话。

这条边界很重要：Socket 是“通知通道”，数据库和 HTTP 接口才是“事实来源”。断线期间漏掉事件时，客户端通过消息历史接口按 cursor 补数，不会依赖 Socket 保证永久投递。

### 加入群房间与权限控制

- 连接建立后，Web 用户自动加入私有房间 `user:<userId>`，用于成员变更等点对点通知。
- 客户端调用带 10 秒 ack 超时的 `group:join`；服务端只接受已认证的 web 类型连接。
- 服务端在 `GroupService.access(channelId, userId, ...)` 的事务中锁定群 `channel` 行，校验群存在、账号仍有效、用户仍是成员，通过后才 `join('group:<channelId>')`。
- 事务锁将“成员变更、发消息、Socket 加群”串行化，避免“被踢出与加入房间并发”造成越权订阅。
- `groupJoinVersions` 是每个 Socket、每个群的版本号：异步鉴权还没完成时如果用户发出了 leave，版本递增；旧 join 回调发现版本已变就拒绝。这解决了 join/leave 竞态。

### 踢人为什么不会继续收到消息？

移除成员时，业务层在变更成员关系后调用 `removeGroupUser`。Gateway 先通过 `user:<userId>` 房间取到该用户的**所有** Socket，再让每个连接离开 `group:<channelId>`，而不是只处理 `activeUsers` 中最后一条连接。随后向群内广播 `group:members-changed`，并单播给被移除用户 `group:membership-updated`，让多端 UI 同步更新。

### 广播可靠性和重放的取舍

群消息使用 `.timeout(10000).emit(event, data, ack)` 广播。ack 的目的不是把 Socket 变成消息队列，而是让 Socket.IO 将这类确认型广播排除在连接恢复缓冲区外；重连后重新鉴权、再拉历史。这样“成员被移除之后恢复旧连接”也不会重放私有群消息。真正的可靠性由消息落库、`requestId` 幂等和历史补拉提供。

### 防止绕过群权限

通用 `join-channel` 会拒绝 `group:*`、`user:*` 前缀；通用 `channel-message` 拒绝群/用户前缀，也会查询数字频道是否 `isGroup`，是群则拒绝。MQ 频道 `4` 也明确禁止客户端发布。因此客户端不能伪造一个房间名加入群或向群广播，必须走受权限控制的群 API 与 `group:join`。

## 其他值得讲的关键实现

### 1. 握手认证和多端身份

Gateway 的 `afterInit` 注册 Socket.IO middleware。Web 端携带 JWT，服务端 `verifyAsync` 后把用户身份写入 socket；runner/bot 使用 `id + uid + runnerToken` 查询数据库确认归属。缺 token、缺身份、验签失败都会先发错误再断开。身份类型区分 web、runner、bot、临时 bot，避免将不同终端按同一权限模型处理。

### 2. 私有通知不依赖单 Socket

账号过期、会员资格或状态变化会向 `user:<userId>` 发 `private-msg`，所有已登录标签页/设备都能收到。相比 `Map<userId, socket>` 只保留一个连接，room 模型天然支持多端；现有 `activeUsers` 更适合旧的用户到用户定向能力和在线查询，若要完善可改成 `Map<userId, Set<socketId>>` 或统一使用 user room。

### 3. 订阅即给快照，事件只推增量

普通市场频道可批量 `join-channel`，客户端用 `joinedChannels` 保存订阅意图并在重连后恢复。MQ 队列频道加入后，服务端只向这个 socket 推一次数据库聚合快照（queued/running/outstanding），后续再向频道广播增量；避免刚订阅的页面只等下一次更新而没有初始状态。队列统计用一条 `groupBy` 查询得到两个状态计数，减少观察到不一致中间态的概率。

### 4. 事件命名与数据信封

群域使用清晰的事件：`group:message-created`、`group:message-deleted`、`group:members-changed`、`group:nickname-updated`、`group:membership-updated`。通用频道统一使用 `channel-msg` 信封，包含 `updateId`、`channelId`、`contentType`、`createdAt` 等字段。`updateId` 可用于前端去重/幂等合并；面试时应说明“当前负责传递，消费端应以它去重”。

### 5. 订阅端防重复监听

客户端是单例 `SocketConnector`，静态 `Set` 管理 private/channel/group/connection listeners；`setupListeners` 用 `listenersBound` 保证只绑定一次，订阅方法都返回 unsubscribe。这样 React 页面反复挂载时不会重复注册事件、重复弹通知或内存泄漏。

### 6. 机器人和运行态隔离

机器人工具调用可以按 `socketId` 定向发送；运行更新通过 `robbot:run:<runId>` 和 `robbot:session:<sessionId>` 两类 room 广播，客户端显式订阅/取消订阅。这样一个高频运行状态不会广播给所有在线用户。

## 可背诵的收尾总结

> 我把实时系统拆成三层：Socket.IO 负责连接保活、重连和房间路由；HTTP + Service + 数据库事务负责权限、落库和幂等；前端把 Socket 当增量通知，断线或切换页面时通过历史接口补齐。群聊重点处理了鉴权后才能入房、踢人时多端全部退房、join/leave 并发竞态，以及连接恢复不能绕过最新成员关系。这比“把消息直接 socket 广播出去”更接近生产可用的方案。

## 容易被追问的改进项（诚实回答）

- 单实例可直接使用 Socket.IO room；多实例部署要接入 Redis adapter，并让 HTTP/Socket 节点共享 adapter，才能跨实例广播和 `fetchSockets()`。
- Socket.IO ack 不是持久消息确认。重要消息仍需 outbox/消息表、消费者去重和历史补偿；需要“至少一次”或“恰好一次”语义时，必须在业务层设计。
- `activeUsers: Map<uuid, socket>` 在同一 uuid 多连接时会覆盖，私有通知已用 user room 避开该问题；遗留的 user-to-user 定向可迁移到 user room。
- 目前重连恢复普通频道，但群订阅刻意不自动恢复；前端进入群页时应重新调用 `group:join`，并拉取 cursor 历史。
