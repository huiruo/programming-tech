# HTTP 面试总结：缓存与性能优化

HTTP 是应用层的无状态请求—响应协议。前端面试里，重点不是背状态码，而是能把一次资源请求讲成一条完整链路：浏览器是否命中缓存、是否需要带条件头向 CDN / 源站校验、服务端为什么返回 `200` 或 `304`，以及如何在**性能、内容新鲜度和发布可控性**之间取舍。

## 30 秒开场回答

> HTTP 本身是无状态的请求—响应协议，HTTPS 在 HTTP 下增加了 TLS 的身份校验与加密。做性能优化时，我会把资源分为两类：带内容 hash 的 JS、CSS、图片可以使用长时间强缓存，因为内容变化时 URL 会变化；HTML 和 API 往往不能长期强缓存，会设置较短缓存或 `no-cache`，让浏览器每次使用前通过 `ETag` / `If-None-Match` 或 `Last-Modified` / `If-Modified-Since` 协商校验。资源未变时服务端返回 `304`，不传响应体，浏览器复用本地副本。最终用 Network 中的传输大小、缓存命中率、TTFB 和 LCP 来验证，而不是只看配置写了什么。

## 1. 一次 HTTP 请求发生了什么

1. 浏览器解析 URL，先检查 Service Worker、内存缓存、磁盘 HTTP 缓存；有可直接复用的强缓存时，请求不会到网络。
2. 若需要网络，浏览器通过 DNS 找到 IP，复用已有连接或建立 TCP 连接；HTTPS 还要完成 TLS 握手和证书校验。
3. 浏览器发送请求行、请求头、可选请求体；CDN / 网关可能先命中自己的缓存，再转发到源站。
4. 服务端执行鉴权、业务和缓存校验，返回状态码、响应头和可选响应体。
5. 浏览器按响应头决定能否缓存、缓存多久；HTML、CSS、JS 等资源随后触发解析、渲染和后续子资源请求。

HTTP/1.1 默认支持 keep-alive，同一连接可复用，但同域并发与队头阻塞仍会受限制。HTTP/2 在一个 TCP 连接上多路复用多个 stream，并使用头部压缩；HTTP/3 基于 QUIC（UDP），减少 TCP 层丢包对其他 stream 的阻塞。它们改善传输效率，**不替代**资源体积控制、合理缓存和减少请求瀑布。

## 2. 常用请求方法、幂等性与状态码

| 方法 | 语义 | 幂等性 | 典型场景 |
| --- | --- | --- | --- |
| `GET` | 读取资源 | 是 | 获取页面、列表、详情 |
| `POST` | 提交动作 / 创建子资源 | 通常否 | 创建订单、提交表单 |
| `PUT` | 用完整表示替换指定资源 | 是 | 完整更新资料 |
| `PATCH` | 局部更新资源 | 不保证 | 改昵称、修改单个字段 |
| `DELETE` | 删除指定资源 | 是 | 删除一条记录 |

幂等表示“重复执行的最终资源状态相同”，不代表每次响应完全相同，也不代表没有日志、计数等副作用。网络重试时，支付、下单等 `POST` 业务应使用业务幂等键，而不是因为 HTTP 方法叫 `POST` 就盲目重试。

高频状态码：

- `200 OK`：成功返回实体；`201 Created`：资源创建成功；`204 No Content`：成功但无响应体。
- `301` / `308`：永久重定向（`308` 保持原方法和请求体）；`302` / `303` / `307`：临时重定向，`307` 保持原方法。
- `304 Not Modified`：协商缓存命中、资源未变。前一次 `200` 必须已下发 `ETag` 或 `Last-Modified`；浏览器下次请求带上 `If-None-Match` 或 `If-Modified-Since`，服务端比对后才返回 `304`。它不是“没有请求”，而是请求已到达可校验的缓存层，只省去了响应 body。
- `400` 参数错误，`401` 未认证或认证无效，`403` 已认证但无权限，`404` 未找到，`409` 状态冲突，`429` 限流。
- `500` 服务端错误，`502` 网关从上游拿到无效响应，`503` 暂不可用，`504` 网关等待上游超时。

## 3. 浏览器 HTTP 缓存：先强缓存，后协商缓存

缓存的关键是：**浏览器先看本地副本是否仍新鲜；不新鲜时再决定是否携带验证器请求网络。**

| 层次 | 关键响应头 / 请求头 | 是否发网络请求 | 结果 |
| --- | --- | --- | --- |
| 强缓存 | `Cache-Control: max-age`、`Expires` | 否（仍新鲜时） | 直接使用本地副本 |
| 协商缓存 | `ETag` ↔ `If-None-Match` | 是 | 未变返回 `304`，复用本地 body；变了返回 `200` 和新 body |
| 协商缓存（兜底） | `Last-Modified` ↔ `If-Modified-Since` | 是 | 同样可能返回 `304` |

### 3.1 强缓存：`Cache-Control` 优先于 `Expires`

```http
Cache-Control: public, max-age=31536000, immutable
```

- `max-age=31536000`：从响应产生起，一年内副本可直接使用。
- `public`：允许浏览器和共享缓存（CDN）保存；带登录态或个性化响应通常应为 `private`，或根本不缓存。
- `immutable`：在 fresh 期间提示浏览器资源不会变化，特别适合内容 hash 文件。
- `Expires` 是绝对时间，受客户端时钟影响；现代策略以 `Cache-Control` 为准，`Expires` 只用于兼容旧客户端。

常见指令也必须分清：

| 指令 | 含义 | 容易混淆的点 |
| --- | --- | --- |
| `no-cache` | 可以存储，但**每次复用前必须协商验证** | 不是“不缓存” |
| `no-store` | 不应存储响应及敏感信息 | 适合高度敏感响应，代价是不能复用 |
| `private` | 仅私有缓存可存，CDN 等共享缓存不应存 | 适合按用户变化的页面 |
| `s-maxage` | 共享缓存的 fresh 时间 | 对 CDN 优先于 `max-age`，浏览器通常忽略它 |
| `must-revalidate` | 过期后不能在未校验时擅自使用旧副本 | 网络不可用时会降低可用性 |

### 3.2 协商缓存：`ETag` 是首选验证器

首次请求：

```http
GET /api/articles/42 HTTP/1.1

HTTP/1.1 200 OK
Cache-Control: no-cache
ETag: "article-42-v17"
Content-Type: application/json

{ "id": 42, "title": "HTTP 缓存" }
```

下一次浏览器仍会请求，但自动携带上次的验证器：

```http
GET /api/articles/42 HTTP/1.1
If-None-Match: "article-42-v17"

HTTP/1.1 304 Not Modified
ETag: "article-42-v17"
Cache-Control: no-cache
```

`304` 没有响应 body；浏览器组合本地 body 和本次允许更新的响应头后使用。它节省了响应体传输和解析，但仍有 DNS / 连接 / 请求往返和服务端校验成本，所以不等于零成本。

`ETag` 是资源版本标识，通常由内容 hash、版本号或最后更新时间加长度等规则生成。服务端应把它视为**不透明字符串**，只比较是否匹配；客户端不用理解其内部结构。`If-None-Match` 可携带多个 tag，`*` 表示任意当前表示，常用于“仅当资源不存在时才创建”。

### 3.3 `Last-Modified`：简单，但精度和语义较弱

```http
Last-Modified: Tue, 10 Nov 2026 08:00:00 GMT

If-Modified-Since: Tue, 10 Nov 2026 08:00:00 GMT
```

它适合静态文件或修改时间可靠、更新频率不高的数据，但有两个常见缺点：秒级时间精度下，同一秒内多次修改可能无法识别；内容可能恢复为原值但修改时间不同。`ETag` 更精确，因此两者同时存在时，`If-None-Match` 的优先级更高；`Last-Modified` 可作为兼容性兜底。

## 4. 缓存策略怎么设计：按资源，而不是一刀切

| 资源 | 建议策略 | 原因 |
| --- | --- | --- |
| `app.8fd2c.js`、`main.a1b2.css` | `public, max-age=31536000, immutable` | 文件名含内容 hash，内容变更会产生新 URL，可安全长期缓存 |
| 图片 / 字体 | 有 hash 时同上；无 hash 用短 TTL + `ETag` | 避免替换同 URL 的图片后用户长期看到旧图 |
| HTML 入口文档 | `no-cache` 或短 TTL + 协商 | 发布后必须尽快发现新 HTML，从而引用新的 hash 资源 |
| 公共内容 API | 短 `max-age` / `s-maxage` + `stale-while-revalidate`，或 `ETag` | 用可接受的旧数据窗口换取源站压力和响应速度 |
| 用户余额、订单、权限 | `private, no-store` 或严格服务端私有缓存 | 防止共享缓存串用户与敏感数据泄露 |

一个典型 CDN 公共内容接口可以是：

```http
Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=60
ETag: "news-list-v20261110-12"
Vary: Accept-Encoding
```

浏览器在 60 秒内可直接使用，CDN 在 300 秒内可复用；过期后的 60 秒，缓存层可先给一个旧副本并在后台刷新，降低用户等待。这里的“允许旧数据多久”必须由业务决定：新闻列表可以，库存、余额和权限不可以。

## 5. `Vary`、CDN 与常见缓存事故

`Vary` 表示缓存键除 URL 外还依赖哪些请求头。例如压缩响应应使用 `Vary: Accept-Encoding`，让 gzip / br 等版本不互相污染。

对 `Cookie`、`Authorization`、语言、设备等请求头要非常谨慎：

- 如果响应真正按用户不同，最好设 `private` / `no-store`，或在 CDN 上把可靠的用户维度纳入缓存键；绝不能把 A 用户数据以公共 URL 缓存后返回给 B。
- `Vary: Cookie` 可能让共享缓存命中率大幅下降。公共内容应尽量把个性化部分拆为单独私有接口或客户端组件。
- CDN 的缓存规则可能覆盖源站响应头。排障时要同时看浏览器 Network、CDN 返回的 `Age` / 命中头和源站真实响应。

前端发布最稳妥的组合是：**HTML 短缓存或每次验证 + 静态资源内容 hash 长缓存**。如果 HTML 也被一年强缓存，用户会一直引用旧版本；如果静态资源没有 hash 却长缓存，同 URL 覆盖发布后用户会遇到新 HTML 配旧 JS、白屏或资源加载失败。

## 6. 条件请求不只用于缓存：并发更新控制

`ETag` 还可以做乐观并发控制。客户端先 `GET` 得到版本，再用 `If-Match` 更新：

```http
PUT /api/profile/7 HTTP/1.1
If-Match: "profile-7-v3"
Content-Type: application/json

{ "nickname": "Ruo" }
```

若版本仍为 v3，服务端写入并产生 v4；若其他人已改过，服务端应返回 `412 Precondition Failed`，避免后提交者无意覆盖前一个人的修改。这和 `If-None-Match` 的“仅在未变化时复用缓存”是不同用途，但都利用了资源版本。

## 7. HTTP 性能优化：按瀑布图定位

1. **减少传输量**：按路由 / 交互拆包，移除无用依赖，图片使用合适尺寸与 AVIF / WebP，启用 Brotli / gzip；不要把 Base64 大图塞进 CSS / JS。
2. **缩短关键路径**：HTML 尽快返回；关键 CSS 优先，非关键脚本用 `defer` / `async` 或动态导入；为真正确定需要的关键跨域资源用 `preconnect` / `preload`，避免滥用抢占带宽。
3. **提高复用率**：hash 静态资源长缓存；公共 API 由 CDN 负责 `s-maxage`；页面数据按实时性设置 TTL 和按事件失效。
4. **减少往返与瀑布**：服务端并行无依赖请求，合并过碎的接口；使用 HTTP/2 / HTTP/3、连接复用和合理 CDN 节点。不要为了“减少请求数”把所有资源合成一个超大包。
5. **可观测并验证**：对比优化前后 LCP、INP、CLS、TTFB、传输字节、缓存状态（memory/disk cache、`304`、`200`）和 CDN 命中率，并按真实网络条件测试。

## 8. 项目面试回答（可直接复述）

> 我处理静态资源缓存时，先按资源可变性划分：构建产物使用 content hash，因此对 JS、CSS、字体和版本化图片返回 `Cache-Control: public, max-age=31536000, immutable`，用户已有相同文件就不会再发网络请求。HTML 不做永久强缓存，而是设为 `no-cache`，确保每次使用前能快速校验并拿到引用新 chunk 的入口。对于经常更新但响应体较大的公共接口，我让服务端返回 ETag，浏览器过期后携带 `If-None-Match` 校验；未更新则返回 `304`，复用本地响应体。公共内容在 CDN 使用短 `s-maxage` 和可接受的 stale 窗口，登录态、余额、权限等则明确 `private, no-store`，避免跨用户缓存。上线后我通过 Network 的缓存状态、响应体大小、CDN 命中率及 LCP / TTFB 对比验证，同时在发布时保留旧 hash 资源一段时间，防止旧 HTML 与新部署切换期间出现资源 404。

## 9. 高频追问速答

### 强缓存和协商缓存谁先？

先判断强缓存是否 fresh；命中时不发网络请求。过期或被 `no-cache` 要求验证时，浏览器才携带 `If-None-Match` 或 `If-Modified-Since` 发起协商请求。

### `no-cache` 和 `no-store` 区别？

`no-cache` 可以存，但不能直接复用，必须先重新验证；`no-store` 是不存储。需要始终检查是否有新版本的 HTML 常用前者，敏感且不应在本地 / 中间层留下副本的数据才考虑后者。

### 为什么是 `304` 而不是直接读缓存？

因为本地副本已过期或策略要求每次验证。`304` 说明网络层已确认资源未变，节省 body，不节省网络往返和校验成本。

### `ETag` 和 `Last-Modified` 如何选？

优先 `ETag`，它能精确表达版本，不受秒级时间精度限制。静态文件或低频更新资源可同时带 `Last-Modified` 作为兼容兜底；两者都有时客户端以 `If-None-Match` 为主。

### `304` 会不会更新缓存时间？

会。浏览器会根据 `304` 中允许更新的缓存响应头刷新元数据 / 新鲜度；响应 body 仍沿用本地已有副本。

### 有 `ETag` 就一定安全缓存吗？

不一定。`ETag` 只解决“内容是否变化”的校验，不处理用户隔离。带 Cookie / Authorization 的响应仍必须正确设置 `private`、`no-store` 或 CDN 缓存键，否则可能泄露数据。

## 10. 握手与连接：面试速答

### TCP 为什么要三次握手？

客户端先发 `SYN` 申请建立连接，服务端回 `SYN + ACK` 表示自己能接收、也同意建立，客户端再回 `ACK` 确认自己能接收。三次的目标是让双方确认彼此的收发能力，并同步初始序列号；这样服务端不会把网络中延迟到达的旧连接请求误当成有效新连接。

建立后 HTTP/1.1 的 keep-alive、HTTP/2 的多路复用都会尽量复用这条连接，避免每个资源都重新握手。连接关闭常说四次挥手：主动方 `FIN`，被动方 `ACK` 后处理剩余数据，再发自己的 `FIN`，最后由主动方 `ACK`；因为 TCP 是全双工，两侧关闭发送方向可以独立发生。

### HTTPS 的 TLS 握手做了什么？

HTTPS = HTTP + TLS，不是新的 HTTP 方法。TLS 握手主要解决三件事：**校验服务端身份、协商密码套件、协商出后续对称加密所用的会话密钥**。

可以这样回答：

> 浏览器连接 HTTPS 站点时，会先建立 TCP（HTTP/3 除外），再开始 TLS。客户端发送 ClientHello，携带支持的 TLS 版本、密码套件和随机数；服务端选择参数并返回证书。浏览器验证证书链、域名、有效期及信任状态，随后双方基于密钥交换派生共享的对称会话密钥。之后 HTTP 的请求头和请求体才在 TLS 记录层中加密传输。现代 TLS 1.3 将完整握手通常压缩为 1-RTT，恢复会话时可做到 0-RTT；但 0-RTT 存在重放风险，只应承载可安全重放的幂等请求。

证书并不是用来加密所有大流量数据的：非对称密码主要用于身份认证和密钥协商，真正传输 HTTP 数据使用性能更好的对称加密。证书校验失败时，不能通过“忽略浏览器警告”来当作正常解决方案。

### TLS 里有哪些加密方式，各自做什么？

| 类别 | 常见算法 / 产物 | TLS 中的职责 | 面试关键点 |
| --- | --- | --- | --- |
| 对称加密 | AES-GCM、ChaCha20-Poly1305 | 加密后续 HTTP 请求和响应 | 速度快，适合大流量；双方必须持有同一个会话密钥 |
| 非对称密码 | RSA、ECDSA、ECDHE | 证书签名校验、身份认证、密钥协商 | 公私钥不相同；现代 TLS 不用 RSA 直接加密会话密钥 |
| 哈希 / 消息认证 | SHA-256、HMAC、AEAD 的认证标签 | 完整性校验、防篡改 | 哈希不可逆，不是“加密后可解密”；AEAD 同时保密和认证 |

现代 TLS 1.3 的典型组合可以理解为：**证书用 RSA 或 ECDSA 签名来证明服务端身份，双方用 ECDHE 协商临时共享秘密，再由它派生 AES-GCM 或 ChaCha20-Poly1305 的对称会话密钥来传输 HTTP 数据。**

其中 ECDHE 的 `E` 是 ephemeral（临时）。每次会话使用临时密钥材料，因此即使未来服务器长期私钥泄露，攻击者通常也无法解开以前已录下的会话流量，这叫前向保密（PFS）。TLS 1.3 已移除旧式 RSA 密钥交换及 RC4、3DES、CBC 等不推荐套件；实践中应交给浏览器、CDN 或成熟 TLS 库协商，不要在业务代码里自行实现加密协议。

### HTTP/3 还需要 TCP 和 TLS 握手吗？

HTTP/3 运行在 QUIC 之上，QUIC 基于 UDP，**不建立 TCP 连接**；TLS 1.3 被整合进 QUIC 的连接建立过程。它仍需要完成加密与身份校验，但可减少建立连接的往返，并避免 TCP 层单个丢包阻塞同一连接内所有 HTTP/2 stream 的问题。业务优化的原则不变：优先连接复用、减小关键资源、正确缓存，而不是仅靠切换协议版本。

## 11. CORS 跨域与预检请求

同源由**协议、域名、端口**共同决定；三者任一不同即跨源。浏览器的同源策略会限制脚本读取跨源响应，CORS（Cross-Origin Resource Sharing）是服务端通过响应头明确授权浏览器读取的机制。

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true
Vary: Origin
```

以下通常会触发浏览器先发 `OPTIONS` 预检：使用 `PUT` / `PATCH` / `DELETE` 等非简单方法；带 `Authorization` 等非简单请求头；或 `Content-Type: application/json`。服务端对预检授权后，浏览器才发送真正业务请求；可以用 `Access-Control-Max-Age` 缓存预检结果，但变更 CORS 策略时要考虑它的生效窗口。

面试要讲清三个边界：

- CORS 是**浏览器读响应的限制**。curl、服务端到服务端请求不受它限制，因此不能把 CORS 当作鉴权。
- 带 Cookie 的跨域请求需要客户端显式 `credentials: 'include'`，同时服务端必须返回准确 Origin 和 `Access-Control-Allow-Credentials: true`；此时 `Access-Control-Allow-Origin` **不能**是 `*`。
- 不要为了“解决跨域”让生产接口无条件允许任意 Origin、任意 Header 和凭证。开发环境代理是同源转发方案，不是生产授权策略。

## 12. Cookie、Session、Token 与 CSRF / XSS

Cookie 是浏览器按域和路径自动附带的状态载体；Session 通常把随机 session id 放入 Cookie，真实登录态存在服务端；JWT / Bearer Token 则是客户端每次通过 `Authorization: Bearer <token>` 主动带上凭证。两者都需要过期、刷新、登出和服务端权限校验，选择取决于撤销能力、跨服务验证和业务架构，不能简单认为 JWT 天生更安全。

```http
Set-Cookie: session=opaque-random-value; Path=/; HttpOnly; Secure; SameSite=Lax
```

| 属性 / 机制 | 解决什么问题 | 注意点 |
| --- | --- | --- |
| `HttpOnly` | JS 不能直接读取 Cookie，降低 XSS 窃取会话风险 | 不防止 XSS 以当前用户身份发请求 |
| `Secure` | Cookie 只走 HTTPS | 本地 HTTP 开发环境需单独配置 |
| `SameSite=Lax` | 大多数跨站子请求不自动带 Cookie，降低 CSRF | 顶级 GET 跳转仍可能带 Cookie |
| `SameSite=Strict` | 更严格的跨站不带 Cookie | 可能影响第三方跳转后的登录体验 |
| `SameSite=None; Secure` | 允许跨站携带 Cookie | 必须 `Secure`，并额外设计 CSRF 防护 |

CSRF 的前提是浏览器会自动带 Cookie：攻击网站诱导已登录用户访问或提交目标站请求，服务端若只看 Cookie 就可能误认为是本人操作。防御方式是优先合理设置 `SameSite`，并对敏感写操作校验 CSRF token、`Origin` / `Referer`，要求不可猜测的自定义请求头等。只用 `POST` 不防 CSRF。

XSS 是攻击者注入并执行脚本。它可能读取非 HttpOnly 的 token，也能直接调用接口执行操作，所以 Token 放在 localStorage 并不能“天然防 CSRF / 更安全”。根本措施是输出编码、避免危险 HTML 注入、CSP、依赖治理；Cookie 会话再配合 `HttpOnly`、`Secure`、`SameSite` 和 CSRF 校验，是常见的防护组合。

## 13. 常用安全响应头

| 响应头 | 用途 | 示例 / 注意点 |
| --- | --- | --- |
| `Strict-Transport-Security` | 强制浏览器后续仅通过 HTTPS 访问 | `max-age=31536000; includeSubDomains`；确认所有子域都支持 HTTPS 后再加子域与 preload |
| `Content-Security-Policy` | 限制脚本、样式、图片、frame 等加载来源，降低 XSS 影响 | 优先 nonce / hash，避免长期使用 `unsafe-inline` |
| `X-Content-Type-Options` | 阻止 MIME sniffing | `nosniff` |
| `frame-ancestors`（CSP） | 控制谁能嵌入页面，防点击劫持 | 用它替代 / 补充旧的 `X-Frame-Options` |
| `Referrer-Policy` | 控制跳转时 Referer 泄露范围 | 常用 `strict-origin-when-cross-origin` |

安全头只能缩小攻击面，不能替代服务端鉴权、参数校验、输出编码和 HTTPS。CSP 上线前可先使用 `Content-Security-Policy-Report-Only` 收集违规报告，再逐步收紧，避免直接发布导致第三方 SDK 或内联脚本白屏。

## 14. 上传、下载与断点续传

浏览器普通文件上传通常使用 `multipart/form-data`，文件大时需要限制类型、大小、数量和超时时间；服务端应根据文件内容 / 魔数校验，生成自己的存储名，不信任客户端文件名和 `Content-Type`，并把上传权限、病毒扫描和对象存储访问控制纳入流程。

下载可使用：

```http
Content-Type: application/pdf
Content-Disposition: attachment; filename="report.pdf"
```

`Content-Disposition: attachment` 提示下载，`inline` 则允许浏览器按能力预览。视频播放和大文件断点续传依赖 Range 请求：浏览器请求 `Range: bytes=1000-`，服务端响应 `206 Partial Content`、`Content-Range` 和 `Accept-Ranges: bytes`。服务端不支持范围请求时通常回完整 `200`；只有确认资源可随机读取、分片合并校验和鉴权都正确时，才在业务层实现分片上传。

## 15. 代理、CDN 与真实客户端 IP

- **正向代理**代表客户端访问外部网络，常用于企业网络、调试或访问控制；目标服务看到的是代理。
- **反向代理**部署在服务端前面，对外代表源站，负责 TLS 终止、负载均衡、静态文件、限流和路由；Nginx、网关与 CDN 都可承担这个角色。
- **CDN** 在边缘节点缓存可共享资源，命中时不回源；未命中或过期时按策略回源。它应与前面的 `Cache-Control`、缓存键和失效策略一起设计。

经过反向代理后，应用看到的连接来源往往是代理 IP，因此代理会传递 `X-Forwarded-For`、`X-Forwarded-Proto` 或标准 `Forwarded`。应用只能信任**由自家可信代理覆盖或追加**的这些头；如果直接信任公网客户端自带的 `X-Forwarded-For`，攻击者可伪造 IP 绕过基于 IP 的限流、风控或审计。

面试可补一句：缓存穿透是反复请求不存在的 key，应用可对空结果短暂缓存、做参数校验或使用布隆过滤器；缓存击穿是热点 key 失效时并发回源，可用互斥更新、逻辑过期或提前刷新；缓存雪崩是大量 key 同时过期，可通过 TTL 加随机抖动、分批预热和降级处理。它们主要是服务端缓存问题，但 CDN / HTTP 缓存策略设计会直接影响回源压力。

## 16. HTTP 流式传输、SSE 与 AI 输出

HTTP 流式传输指服务端**不必等完整响应生成完**，而是先发响应头，再持续写出一段段 body；浏览器收到首段即可开始消费和渲染。它适合 AI token 输出、日志、进度、长任务结果和 SSR 流式页面，核心收益是降低“首字节 / 首段可见”的等待时间，而不是让总计算时间凭空变短。

### HTTP/1.1、HTTP/2 与 HTTP/3 的传输形式

- HTTP/1.1 若响应长度未知，常使用 `Transfer-Encoding: chunked`：每个分块前带十六进制长度，长度为 `0` 表示结束；此时不能再同时发送 `Content-Length`。
- HTTP/2 / HTTP/3 以各自协议的 DATA frame 承载 body，天然知道流结束，**不使用 HTTP/1.1 的 `chunked` 格式**。应用层“边生成边写”的概念仍相同。
- 流式响应通常不宜被共享缓存；对动态个人结果可用 `Cache-Control: no-store`。若压缩、CDN 或反向代理缓冲完整响应后才下发，用户依旧看不到流式效果。

### 浏览器如何读取普通流式 HTTP 响应

服务端可以返回 NDJSON（每行一条 JSON），前端通过 `fetch` 的 `ReadableStream` 逐块解码。网络 chunk 不保证刚好等于一条业务消息，因此必须自己缓冲并按协议边界切分：

```ts
const response = await fetch('/api/generate', { method: 'POST' });
if (!response.ok || !response.body) throw new Error('stream unavailable');

const reader = response.body.pipeThrough(new TextDecoderStream()).getReader();
let pending = '';

while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  pending += value;
  const lines = pending.split('\n');
  pending = lines.pop() ?? '';
  for (const line of lines) {
    if (line) renderChunk(JSON.parse(line));
  }
}
```

取消时可使用 `AbortController`；服务端也应监听连接断开，停止模型生成或长任务，避免用户离开页面后继续消耗资源。前端更新 UI 时可按 token / 时间片批量更新，避免每个很小分片都触发一次昂贵渲染。

### SSE 和 WebSocket 怎么选？

SSE（Server-Sent Events）是建立在 HTTP 上的**服务端单向推送**协议，响应类型为 `text/event-stream`，每条事件通常以 `data:` 开头、空行结束。浏览器原生 `EventSource` 自动重连，适合通知、行情、进度和 token 推送；标准 `EventSource` 只发 GET，且不能方便地自定义 `Authorization` 请求头，认证方案需谨慎设计。

WebSocket 是升级后的全双工长连接，适合聊天室、协作编辑、双向实时游戏指令等客户端也要高频发送消息的场景。若只是一次请求对应一段连续结果（例如 AI 问答），普通 `fetch` 流式响应通常更简单，也更容易复用既有 HTTP 鉴权、网关和可观测性。

### 流式输出没有生效，怎么排查？

1. 浏览器 Network 看响应是否持续增长、首段是否早到；不要只看服务端日志“已经 write”。
2. 检查应用是否真的 `flush` / 持续写入，以及是否错误设置了完整 `Content-Length`。
3. 检查 Nginx / CDN / 网关缓冲；例如 Nginx 可为该流式 location 关闭 `proxy_buffering`，但应只对需要的接口开启，并评估连接占用和超时。
4. 避免把完整结果先聚合在 BFF 或 Server Component 再转发；每一跳都要支持边读边写。
5. 为心跳、超时、错误事件、断线取消和重连设计协议，且不要把流式接口放进会破坏分段的响应缓存。

### 面试可直接回答

> AI 输出这类场景我会使用 HTTP 流式响应：服务端生成一部分就写一部分，前端用 `fetch` 读取 `ReadableStream`，按 NDJSON 或 SSE 事件边界解析后渐进渲染。HTTP/1.1 的未知长度响应可用 chunked 编码，HTTP/2 / 3 则通过 DATA frame 分段传输。实现重点不只是接口返回 stream，还要关闭必要链路上的代理缓冲、处理取消和断连、避免把网络 chunk 误当消息边界，并通过首段到达时间和完整响应时间验证效果。只有服务端单向推送时我会优先 SSE；需要双向高频通信才选择 WebSocket。
