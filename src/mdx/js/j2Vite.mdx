## 介绍
adv. 急速地；轻快地
/viːt/

vite:就是借助浏览器原生 ES Modules 能力，当浏览器发出请求时，为浏览器按需提供 ES Module 文件，浏览器获取 ES Module 文件会直接执行，即使首次启动的预构建也是使用速度惊人的esbuild完成，但是要优化的点：首屏、懒加载性能

webpack:需要构建完整的依赖关系,打包成一个bundle.js

## prod环境打包区别
### vite在生产环境的构建目前用的Rollup
* vite在生产环境，如果使用ESM会存在大量额外网络请求问题：
```
尽管原生ESM现在得到了广泛支持，但由于嵌套导入会导致额外的网络往返，在生产环境中发布未打包的ESM仍然效率低下；
最好的方式还是代码进行 tree-shaking、懒加载、和 chunk 分隔等；
```

* 使用 rollup打包而不是速度惊人的esbuild，这是因为esbuild针对构建应用的重要功能仍然还在持续开发中 —— 特别是代码分割和css处理方面，rollup在应用打包方面更加的成熟


### 首屏、懒加载性能优化
webpack bundle得到了一个完整的模块关系依赖包;vite由于unbundle机制，首屏、懒加载会存在一定的问题，处理时需要额外做以下工作：
* 由于未对源文件做合并捆绑操作，导致大量的http请求；
* 动态加载的文件需要对源文件进行转换操作：resolve、load、transform、parse；
* 预构建、二次预构建操作也会阻塞首屏请求，直到预构建完成为止；
* 但是由于缓存的存在，当第一次加载完成(预构建)之后，再次reload的时候性能会有较大的提升;

## 服务启动速度
webpack需要先把所有的模块建立依赖关系打包成一个大文件，速度相对较慢；

vite将应用中的模块区分为 依赖(node_modules) 和 源码(项目代码) 两类，进行预构建，速度会快很多；

依赖：使用esbuild预构建，esbuild使用Go编写，比以Node.js编写的打包器预构建依赖快10-100倍；
```
初次预构建完成后，会在node_modules中生成 .vite文件，后期不需要再次进行依赖的预构建；
```

源码：在浏览器请求时按需转换并以原生ESM方式提供源码，让浏览器接管了打包程序的部分工作；
```
由于是按需提供，所以在首屏、懒加载方面相比于webpack会存在一定的差异；
```

## 热更新速度
### webpack
编辑文件后将重新构建文件本身;所以webpack支持了动态模块热重载HMR(Hot Module Replacing)，这较大的提升了开发体验

### vite
* 在vite中，HMR是在原生ESM上执行的，当编辑一个文件时，只需要精确地使已编辑的模块与其最近的 HMR边界之间的链失效(大多数时候只需要模块本身)，使HMR更新始终快速，无论应用的大小；

* vite同时利用HTTP头来加速整个页面的重新加载(再次让浏览器为我们做更多事情)：<br />源码模块的请求会根据304 Not Modified进行协商缓存；<br />依赖模块请求则会通过 Cache-Control: max-age=31536000,immutable进行强缓存;

##  vite的实现原理
- 基于浏览器 es module import 实现的编译服务
- 基于 esbuild 做的依赖预构建
- 基于 hash query 做的强缓存和缓存更新

下面把这 3 句话拆开，按「浏览器怎么请求」→「Vite dev server 怎么返回」→「为什么快」的顺序，把关键链路讲清楚（偏实现而不是概念）。

### 1) 基于浏览器 ESM 的“按需编译服务”
核心前提：浏览器原生 `import` / `<script type="module">` 会把每个模块当作一个 URL 去请求，并且递归请求它的依赖图（网络层面的依赖图）。

Vite dev server 的职责就是：**把这些 URL 对应的源码，实时转换成浏览器能执行的 ESM**，并保证每一次请求都能命中正确的模块内容。

#### 1.1 请求从哪里来：HTML 是入口
浏览器先请求 `index.html`，Vite 会把它当成“第一等公民”处理（不是静态文件原样返回），通常会：
- 注入 HMR 客户端脚本（用于 websocket 通信）
- 确保后续模块请求走 Vite 的模块处理链路（例如 `@vite/client`）

#### 1.2 模块如何被编译：插件管线（resolve → load → transform）
当浏览器请求 `/src/main.ts`、`/src/App.tsx` 这类“源码模块”时，Vite 的处理流程可以抽象为：
1. **resolve**：把 import specifier（如 `./App`、`react`、`@/utils`）解析成最终 URL/文件路径（`resolveId`）
2. **load**：读取模块内容（`load`）
3. **transform**：把内容编译成浏览器可跑的 ESM（`transform`）

这三个阶段由 Vite 的插件系统驱动（Vite plugin 基本兼容 Rollup plugin 的钩子），所以你看到的“调用 vite 插件做 transform”本质上是插件容器在执行钩子链。

常见的 transform 包括：
- TS/TSX/JSX → JS（开发时很多场景直接用 esbuild 转）
- Vue SFC/React JSX 等框架编译
- CSS 模块化：`import './a.css'` 转成 JS 注入（或 HMR 可更新的样式模块）
- import 重写：把裸模块导入（`import react from 'react'`）改写成可请求的路径（一般指向预构建产物）

#### 1.3 Module Graph（模块图）为何必需
Vite 在服务端维护一张 **Module Graph**（依赖/被依赖关系）：
- 给 HMR 用：改动发生时，快速定位受影响模块与最近的 HMR boundary
- 给缓存用：同一模块二次请求时可复用上次 transform 结果（再结合 etag/mtime 做校验）

你可以理解为：浏览器负责“按 URL 拉取模块图”，Vite 负责“按需编译 + 维护编译态模块图”，两者配合才让 dev 变得很快。

核心是基于浏览器的 type 为 module 的 script 可以直接下载 es module 模块实现的。


## 比如lodash, react  lucide-react 等 vite 他会达成一个文件还是 多个？
不是。

在 Vite 开发环境里，浏览器确实是“按模块 URL 请求”的，但 Vite 会把模块分两类处理：

你的源码（src/**）：基本保持“一个源文件 ≈ 一个模块请求”，这样改动时 HMR 才能精确、快。
依赖（node_modules）：通过 optimizeDeps 用 esbuild 预构建，把依赖变成“浏览器友好的 ESM 版本”，并且尽量减少请求数。
所以不会出现“每个 npm 包拆成很多很多文件都要请求”的最坏情况；通常更接近：

每个被用到的依赖包会有一个（或少量几个）预构建产物文件（放在 node_modules/.vite/ 或缓存目录），浏览器请求的是这些产物，而不是请求依赖包里原始的几十/几百个源码文件。
个别依赖因为导出结构、动态引用、side effects、或预构建策略，会产生不止一个文件，但目标仍是减少网络请求而不是增加。

### 疑问：
每个被用到的依赖包会有一个（或少量几个）预构建产物文件（放在 node_modules/.vite/ 或缓存目录），浏览器请求的是这些产物，而不是请求依赖包里原始的几十/几百个源码文件。 这个和webpack 什么 区别？不就是webpack

你抓到点了：“依赖预构建成少量文件”这件事，确实很像 webpack 的 bundle。但 Vite 和 webpack 的关键区别不在“有没有把依赖合起来”，而在 dev 时谁来负责模块加载、以及什么时候做转换/打包。

webpack dev（bundle-first）:
1. 启动时：先把“源码 + 依赖”整张依赖图交给 webpack 编译、打包成一个/多个 bundle（通常在内存里）。
2. 浏览器侧：请求的是这些 bundle（不是按 ESM 模块逐个请求源码）。
3. 改动时：往往需要重新构建一部分 bundle（哪怕有增量编译/HMR，本质仍是在“bundle 产物”层面更新）。

Vite dev（serve-native-ESM + deps prebundle）:
1. 启动时：只把依赖用 esbuild 预构建成少量 ESM 文件（node_modules/.vite/deps/*），让它们像“稳定静态资源”一样强缓存。
2. 浏览器侧：源码按原生 ESM 一文件一请求加载；Vite server 对每个源码模块做按需 transform 后返回。
3. 改动时：通常只让“变动的那个模块 + 到最近 HMR boundary 的链路”失效并重取，粒度更细。
所以可以把它总结成一句话：
- webpack：dev 时主要产出和更新的是 bundle
- Vite：dev 时主要产出和更新的是 模块（ESM）；只把 依赖“bundle 化”来解决 CJS/请求数问题

生产环境两者又会收敛：Vite 也会用 Rollup 做打包（同样会变成 chunk/bundle）。

### 所以说二者只是开发环境的差别？上到生产都一样？
开发环境（差别最大）
  - webpack：bundle-first（编译打包后再给浏览器）
  - Vite：native ESM + 按需 transform + 依赖预构建（浏览器按模块请求）

生产环境（都会打包，但实现与产物策略不完全一样）
- webpack：用 webpack 自己的打包器生态完成（loader/plugin、chunk 策略、runtime 注入等都按 webpack 体系）
- Vite：默认用 Rollup 打包（Rollup 的 chunking/treeshake 语义 + Vite/Rollup 插件体系）

结果都是“多个 chunk + 按需加载”，但 tree-shaking 细节、chunk 切分、CSS 处理、插件语义、以及边缘行为（CJS/ESM 混用、sideEffects 标注等）可能不一致。

### 对“产品开发”（交付效率 + 线上体验）真正带来的主要是这些：
- 启动与迭代更快：dev 启动不必先打完整 bundle；改一行代码通常只影响极少模块，HMR 更稳定、更快（大型项目差异更明显）。
- 缓存收益更大：依赖预构建产物强缓存，二次冷启动/刷新更快；团队日常开发体感提升很明显。
- 生产构建更成熟（Vite 默认 Rollup）：更强的 tree-shaking/代码分割语义一致性（尤其 ESM 依赖占比高时），产物更易做到“按需加载 + 更小体积”。
- 工程复杂度变化：配置从“loader-centric（webpack）”变成“plugin + ESM 约定（Vite/Rollup）”；多数场景更轻，但遇到 CJS、monorepo、非标准包结构时需要额外处理（例如 optimizeDeps/include、SSR/worker 等边界）。

一句话：主要提升开发效率与迭代体验，同时在“现代 ESM 依赖为主”的项目上，生产体积/分包也更容易做好；但不是无代价，边界依赖/兼容问题的处理方式会变。

### vite可优化项目
实际项目里，常见的优化点可以分成 dev（开发体验）和 build（生产体积/加载性能）两类：

**Dev 优化**
- `optimizeDeps.include/exclude`：把“扫描不到但运行时会用到”的依赖手动 include，或把不该预构建的依赖 exclude，减少二次预构建/冷启动抖动
- `server.fs.strict` + 合理的 `resolve.alias`：减少奇怪的路径解析与重复模块（尤其 monorepo / workspace）
- `cacheDir`：把缓存放到更稳定的位置（CI/多项目场景更有感），避免频繁重建 deps cache

**Build 优化**
- `build.rollupOptions.output.manualChunks`：把大依赖拆成更合理的 chunk（比如 `react`/`vendor`/业务模块），改善首屏与缓存命中
- `build.sourcemap`：生产一般关闭或用更轻量的策略，减少产物体积与构建耗时
- `build.cssCodeSplit`：按需拆 CSS，避免首屏加载不必要样式（视项目结构取舍）
- `splitVendorChunkPlugin`/分析工具：用可视化报告找出真正的体积大头，再决定是拆分、按需引入还是替换依赖

### 2) 基于 esbuild 的依赖预构建（optimizeDeps / deps optimize）
为什么要预构建：浏览器的 ESM 对“源码”很友好，但对“依赖”不友好，典型瓶颈是：
- **大量文件与深层依赖**：依赖包拆得很碎会带来海量网络请求
- **CommonJS/混合格式**：很多包是 CJS，浏览器无法直接 `import` 执行

所以 Vite 会把模块分两类处理：
- 源码（项目代码）：保持颗粒度细，按需编译，服务 HMR
- 依赖（`node_modules`）：尽量一次性转成浏览器友好的 ESM，并做一定的合并/扁平化来减少请求

#### 2.1 预构建在做什么
dev 启动（或首次遇到某个依赖）时，Vite 会：
- 扫描入口及其静态依赖，收集“裸导入”（`import 'react'` 这种）列表
- 用 esbuild 将这些依赖 **bundle 成 ESM**，输出到 `node_modules/.vite/`
- 生成元信息（如 `metadata.json`）记录依赖列表、产物路径、hash 等，用于判断是否需要复用缓存/重新预构建

- 但是 node_modules 下的文件有的包是 commonjs 的，并且可能有很多个模块，这时 vite 做了预构建也叫 deps optimize。
它用 esbuild 分析依赖，然后用 esbuild 打包成 esm 的包之后输出到 node_modules/.vite 下，并生成了一个 metadata.json 来记录 hash。

### 3) hash query：强缓存与缓存更新
预构建依赖的特点是：内容相对稳定、体积可能较大、请求频率高。Vite 在 dev 下通常会对这类资源启用强缓存：
- 返回 `Cache-Control: max-age=31536000, immutable` 让浏览器长期缓存
- URL 上加版本参数（常见 `?v=xxxx` 这种 hash query）

这样就能做到：
- **依赖不变**：浏览器直接命中强缓存
- **依赖变了（重新预构建）**：hash 变化 → URL 变化 → 浏览器自然拉取新内容

而对源码模块（`/src/**`）通常更适合协商缓存（例如 `304 Not Modified`），因为源码变化更频繁，强缓存反而会妨碍更新。

在开发时通过 connect 起了一个服务器，调用 vite 插件来做 transform，并且对 node_modules 下的模块做了预构建，用 esbuild 打包。
浏览器里用 max-age 强缓存这些预打包的模块，但是带了 hash 的query。这样当重新 build 的时候，可以通过修改 query 来触发更新。

### 4) HMR：为什么能做到“精确失效”
Vite 的 HMR 基本链路是：文件监听（常用 `chokidar`）+ websocket 通信 + Module Graph 定位影响范围。

当某个文件变更时，服务端会：
1. 使对应模块在 Module Graph 中失效（invalidate）
2. 沿着“被谁 import 了”的链向上查找最近的 HMR boundary（框架插件通常会自动注入边界，或你手写 `import.meta.hot.accept`）
3. 通过 websocket 通知浏览器：需要更新哪些模块 URL
4. 浏览器只重新请求那几个模块（触发按需 transform），并执行热替换逻辑

因此 Vite 的“快”更多来自：**只重新做必要的工作**，而不是每次都把整张依赖图重新打包一遍。

在生产环境用 rollup 来打包，因为 vite 插件兼容了 rollup 插件，所以也是用同样的插件来处理，这样能保证开发和生产环境代码一致。

<CodeBlock>
```text
在 build 的时候 vite 会用 rollup 做打包,vite 插件时兼容 rollup 插件的，这样在开发的时候，在生产环境打包的时候，都可以用同样的插件对代码做 transform 等处理。
注意：dev 和 prod 分别用的 esbuild 和 rollup，会有不一致的问题，未来要通过 rolldown 解决
```
</CodeBlock>
