## 我建议先做“统一并发限制 + 有界队列”，再考虑多实例负载均衡：

- 统一模型并发池：个股报告和组合报告共用 Redis 全局额度，初始最多同时执行 3 个。这样增加后端实例也不会突破模型并发限制。
- 超出后排队：使用 BullMQ（Redis）保存任务，页面显示“排队中 / 生成中 / 已完成”。设置队列长度和等待超时，避免无限积压。
- 后台执行、前端订阅：Worker 负责生成和保存，SSE 只传进度。切换页面、刷新或断网后，可以通过任务 ID 查询并恢复展示。
- 限制重复与重试：沿用幂等和生成锁；仅对明确可重试的上游限流或临时故障进行有限重试，避免重复生成、重复计费。
- 根据监控调并发：记录排队时长、生成耗时、模型 429/超时率、数据库连接使用情况，再决定从 3 提高到多少。

## 实施方案
# AI 报告统一并发池与持久队列

  ## 目标与默认值

  个股报告和组合报告统一通过 BullMQ 排队，由后台 Worker 生成、校验和保存。SSE 只负责订阅进度；切换页面、刷新、断网不停止任务。

  在后端常量中统一配置：

  - 全站最大执行并发：3，所有后端实例共享。
  - 未结束任务上限：30，包含排队、执行和延迟重试任务。
  - 累计排队超时：10 分钟，从首次提交计算。
  - 模型执行超时：沿用现有配置。
  - 明确未受理的上游请求最多自动重试 1 次；遵循 Retry-After，默认等待 5 秒，最长 60 秒，仍受排队期限约束。

  普通聊天不进入报告队列，继续使用原有限流规则。

  ## 后端执行与一致性

  - 新增统一报告任务模块，使用一个 BullMQ 队列，通过任务类型区分个股和组合报告。使用 BullMQ 全局并发限制，不能按每个实例分别限制为 3。
  - 把现有两个服务拆分为“提交任务”和“执行已有任务”。Worker 复用现有分析、校验和保存逻辑，不再次创建业务任务或重复扣次。
  - 新增关联 AiToolRun 的持久任务表，记录任务类型、状态、输入快照、提交日期、排队期限、尝试次数、上游调用阶段、执行租约及错误信息。使用数据库迁移，不执行 db push。
  - 任务状态采用 queued → running → completed/failed，重试等待显示为排队中。组合报告继续使用当前五章节契约。
  - 数据库任务记录兼作投递凭据：提交事务保存业务任务、输入快照和个股额度流水；提交后投递 BullMQ，jobId 使用业务 runId。定时补投事务已提交但尚未成功入队的任务。
  - Redis 原子预留未结束任务容量，容量预留与任务绑定、定期续期；终态幂等释放。Redis 不可用或容量已满时拒绝新任务，不调用模型、不扣次。进程异常后由任务协调器修复预留和投递状态。
  - 保留个股 symbol + analysisDate 精确复用及去重规则；命中现有报告直接返回，不入队、不扣次。同证券日期正在生成时返回明确的已有任务提示，不向其他用户暴露任务或持仓信息。
  - 组合报告提交时固定 Context 快照和北京时间报告日期，排队跨午夜后仍使用原快照、原日期。排队和执行均占用当天组合记录，期间禁止删除。
  - 个股报告入队时占用提交日额度；最终系统失败、等待超时或执行前权限失效时退还原流水。重试不重复扣次，缓存复用不计次。组合报告维持独立的每日记录规则。
  - 会员权限在提交和实际执行前分别检查；任务详情和事件订阅始终校验当前用户所有权。

  ## 重试、恢复与订阅接口

  - 仅明确拒绝受理的 HTTP 429 且尚无输出、工具执行或用量证据时允许重试。5xx、调用超时、断流和结果不确定时不自动再次调用模型。
  - Worker 调用上游前持久化调用标记。进程重启后，尚未调用上游的任务可以恢复执行；已调用但无可靠结果的任务标记失败并处理退款，不自动重跑。已保存完成结果的任务只补齐终态。
  - 保留现有两个 POST SSE 路径，改为“提交或复用任务后订阅”；新增首个任务事件，立即返回 runId、任务状态和排队信息。断开连接仅移除订阅，不 abort Worker。
  - 新增统一接口：
      - GET /api/ai/report-tasks?status=active：当前用户未结束任务。
      - GET /api/ai/report-tasks/:runId：状态、进度快照、时间、错误或最终报告引用。
      - GET /api/ai/report-tasks/:runId/events：可重连的 SSE，支持 Last-Event-ID。

  - 进度通过 Redis Stream 传递，每任务最多保留 2000 条事件，终态后保留 24 小时；数据库保存节流后的正文快照，最多每秒更新一次。事件已过期时发送完整快照，再继续订阅。
  - 完成报告和任务终态事务提交后才能发送完成事件；订阅故障不把已保存报告改成失败，也不退款。
  - 替换旧的 running 超时修复逻辑，排队任务按等待期限判断，执行任务按执行租约判断，避免误伤长时间排队的任务。

  ## 前端与运维

  - 两个共享会话管理器按 runId 管理订阅，进入页面时查询未结束任务并恢复。刷新恢复不再次调用生成接口，也不重复追加正文。
  - 页面展示“排队中”“生成中”“已完成”及明确失败原因；展示前方等待数量，不承诺准确开始时间。排队和生成期间按钮不可重复提交。
  - 移除组合报告的停止按钮；关闭面板、切换路由或断网均不取消报告。聊天停止功能保留。
  - 个股报告成功后继续清空股票搜索和选择；失败保留输入。报告 Markdown 渲染及公开规则沿用现有实现。
  - Worker 默认随后端启动，增加开关支持以后独立部署；所有 Worker 共用同一全局并发池。Redis 需启用持久化并采用 noeviction。
  - 增加队列深度、排队耗时、生成耗时、429/超时率、重试数、失败率和数据库连接使用率监控。连接指标使用数据库已有监控能力，应用不依赖不稳定的 Prisma 私有接口。
  - 同步更新两份报告交接文档，说明状态、接口、常量、退款、恢复及发布步骤。发布时先等待旧直接生成任务结束，再统一切换实例，避免新旧链路绕过统一并发限制。

  ## 验收与测试

  - 10 位用户混合提交两类报告，全站同时执行不超过 3，其余任务排队；多个 Worker 实例下结果一致。
  - 第 31 个未结束任务被拒绝且不扣次；排队超时幂等失败、退款并释放容量。
  - 刷新、断网、路由切换和重新登录后可恢复本人任务；重复订阅不产生重复正文或重复任务。
  - 同一幂等键、同股票日期及同组合日期并发提交不重复生成；跨用户访问任务被拒绝。
  - 仅明确未受理的 429 最多重试一次；超时、断流、进程崩溃后的不确定调用不自动重跑。
  - 覆盖数据库提交后入队失败、Worker 重启、Redis 中断、终态提交后事件发送失败、跨午夜和管理员重置额度。
  - 运行现有报告、额度和前端会话回归测试，新增真实 Redis/BullMQ 集成测试；模型使用可控模拟服务，自动化验证不消耗真实 AI 额度。
